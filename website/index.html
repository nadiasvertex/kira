A compiler that
teaches while it checks.

Cinder is an early-stage systems language built around one idea: the compiler is a teacher first. Every diagnostic explains what was expected, what was found, and how to fix it — and the type system proves what it can, so you pay for checks only where the compiler can't already tell you're safe.

A language with real proofs, not just annotations

Cinder isn't a syntax skin over familiar semantics. Dependent and refinement types let the compiler discharge bounds checks and preconditions statically — and fall back to a runtime check, explicitly, only when it has to.

λ

Functional-first core

Closures, iterators, and combinators (map, fold, chain, filter) are the everyday way to write Cinder — not a bolted-on module.

∀

Refinement & dependent types

Constrain a type with a predicate over self. The compiler proves what it can from literals, branches, and array lengths, and elides the check entirely.

⚙

Compile-time execution

static if, static assert, and const generics run real Cinder code at compile time — the untaken branch is discarded before it's even name-resolved.

✓

Diagnostics as UI

Every error states what was expected, what was found, why the rule exists, and a concrete fix — never just a type name and a line number.

⊕

Traits & generics

Monomorphized generics, higher-kinded traits, and type-level reflection (T.name(), T.kind()) for writing real generic libraries.

▣

Modules as values

Modules can be parameterized and passed around like any other compile-time value — functors, not just namespaces.

Cinder, in practice

There's no playground yet — these run today, exactly as shown, via cinder path/to/file.cn.

demo/algorithm-fold.cn
def main() -> int32:
    let nums = [1, 2, 3, 4, 5]
    let nv = nums.iter().values()

    # Sum: start at 0, add each element
    println("sum={nv.fold(0, (acc, x) => acc + x)}")
    # Product: start at 1, multiply each element
    println("product={nv.fold(1, (acc, x) => acc * x)}")

    # Empty iterator returns the initial value, unlike reduce
    let empty: list[int32] = []
    println("empty_fold={empty.iter().values().fold(42, (acc, x) => acc + x)}")
    return 0
Combinators over iter() are ordinary methods — no separate "iterator trait" ceremony to opt into.
demo/dependent-types.cn
# A refinement constrains a type with a predicate over `self`.
type positive = int32 where self > 0

# `index4` is a `usize` provably a valid index into a 4-element array.
type index4 = usize where self < 4

# `i < 4` and `len(v) == 4` are both known here, so `i < len(v)` is
# *proved* — this compiles to a bare load, no bounds check emitted.
def safe_get(v: array[int32, 4], i: index4) -> int32:
    v[i]

# The escape hatch: what the solver can't prove, a runtime check can.
def classify(raw: int32) -> int32:
    match positive.try_from(raw):
        @some(p) => needs_positive(p)
        @none    => 0
The unwrap is the proof — inside the @some(p) arm, p already has type positive.
demo/static-if.cn
# The condition runs in the compile-time interpreter; the branch not
# taken is discarded before name resolution ever sees it.
def describe[T]() -> str:
    static if T.name() == "int64":
        return "wide"
    else:
        return "narrow"

def main() -> int32:
    println("describe[int64]={describe[int64]()}")
    println("describe[int32]={describe[int32]()}")
    return 0
One describe per instantiation, each branch resolved once, statically, per type.

Errors that explain themselves

A diagnostic states what was expected, what was found, why the constraint exists, and — where applicable — exactly how to satisfy it. When a rule depends on a concept you haven't reached yet, the message names it and points at the chapter that explains it. 

error[E0012]: type mismatch
  --> src/main.cn:14:5
   |
13 |     let x: int32 = compute()
14 |     process(x)
   |             ^ expected float64, found int32
   |
   = compute() returns int32
   = process() expects float64
   = hint: use float64(x), or change compute()'s return type

Where things stand

Cinder is early. The pipeline below is real and working; the rest is being built in the open.

  • Shipping Lexer, recursive-descent parser, and error-recovering diagnostics
  • Shipping Module graph, name resolution, and type checking
  • Shipping Tier-0 bytecode VM and LLVM-backed native (AOT) compilation
  • Shipping Generics, traits, dependent & refinement types, compile-time execution
  • In progress Broader standard library coverage (std.algo, std.string, std.fs, …)
  • Planned Interactive playground
  • Planned Package manager and multi-module builds
