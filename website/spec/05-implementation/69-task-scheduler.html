69. The Task Scheduler

Status: Implemented

The shared runtime that runs tasks on worker threads for both backends, with an event loop for tasks that wait on the operating system. It lives in src/runtime/scheduler.{h,cpp} and src/runtime/reactor.{h,cpp}, behind a C++ interface the VM uses and a C ABI that compiled code calls.

Pools and workers

A task runs in a pool, one per execution context (The Execution Model). The io pool runs one poll at a time by default, so io tasks interleave but do not run in parallel. A task is not bound to a thread: its polls may run on different workers, and the checker does not assume otherwise. The cpu pool has one worker per hardware thread. CINDER_IO_WORKERS and CINDER_CPU_WORKERS override the counts; the test harness sets the first to run io tasks in parallel. Worker counts do not change what the compiler accepts. A pool starts its threads when it first has work and keeps them for the life of the process. A worker has an 8 MiB stack, the usual size of a main thread’s, so a task can recurse as deep in compiled code as the entry function can. If no thread can be started and no worker remains to reach the queue, the process prints a panic and exits with status 101. The count limits how many polls run at once, not how many threads exist: a plain function a task called cannot suspend, so a blocking wait there gives the worker’s place to another worker, started if none is idle. When the wait ends the worker waits for a place, ahead of the queue, so an io pool of one still runs one poll at a time. Each nested blocking wait holds a thread, and the threads stay for the life of the process. All scheduling state is behind one mutex, and a step function runs outside it.

Every async def is an io task today. await on(cpu): ... starts a task in the cpu pool.

Task lifecycle

A task is a coroutine object (HIR and the Bytecode VM). It is inert until the scheduler takes it over, which happens when a program calls spawn, when another task awaits it, or when the entry function blocks on it. Taking a task over allocates a record for it and queues it.

A coroutine object is freed with its state block and record once three things hold: the program has dropped its handle, the task has finished, and nothing in the runtime still names it. Dropping a handle cancels the task if it has not finished, then calls release (rt_task_release). A coroutine the scheduler never took over, such as a generator, is freed by release at once, since its dropper has already resumed it to the end. For one the scheduler owns, release marks the record, and whichever of release and the task’s finish comes last frees it. A finished task leaves every waiter list it is in, so no list names a freed task: each record keeps the tasks it waits on (waiting_on) and the memory word it waits for. A crew holds each task spawned into it until the crew is freed, since it reads them back after the block’s handles are gone, and the reactor holds a waiter while one of its lists names it (hold/unhold). await consumes the task it waits for: lowering drops the task once its result is read, and par and race drop every branch task the same way.

A worker pops a task and calls its step function through the runner the task was spawned with: the VM’s runner polls the task on the VM, and the native runner calls the compiled function pointer. The status it returns decides what happens next:

  • suspended or done: the task produced its result or finished. The scheduler marks it done and moves its waiters to the run queue.
  • pending: the task awaited something unfinished and registered itself as a waiter. If a wake arrived while the step function was still running, the task is queued again at once; otherwise it waits.
  • an exception: the scheduler stores it as the task’s failure and finishes the task.

Awaiting

await_poll(self, awaited) is called by a task’s step function at each await. It returns true if awaited is done (rethrowing its failure if it panicked). Otherwise it queues awaited if nothing had started it, adds self to its waiters, and returns false, and the step function returns pending. On wake the step function resumes at the same await and polls again, so a spurious wake is harmless. await_any_poll does the same for a set of tasks and is true when any one is done; it backs race. await_all_poll is true when every task is done; if one has panicked it cancels the others and rethrows once they have stopped. It backs par, with block_on_all for callers that are not tasks. A crew is a runtime object (crew_new, crew_spawn, crew_join_poll/crew_join, crew_free, and crew_size/crew_task for reading the tasks back) holding the tasks spawned into one block; joining it is await_all/block_on_all over them. crew_spawn marks each task crew-owned so that dropping the program’s handle (cancel_on_drop, used by drop glue) does not cancel it. block_on serves callers that are not tasks, such as the entry async def main or a plain function a task called: it queues the task and blocks the calling thread until it is done. A cancel does not reach a task a plain function is blocked on with block_on, so the worker waits for it to finish normally; only the tasks of a crew the task has open are cancelled.

A panic inside a task does not end the process. Both tiers share one path. report_panic prints the message once where the panic happens, and on a worker the panic then unwinds to worker_loop: the VM throws panic_error, and compiled code throws task_panic through its frames, which carry unwind tables for this. No landing pads run, so the panicking task’s own drops are skipped on both tiers. The failure is rethrown in the task or function that awaits it, so it propagates up the chain of awaits to the entry function. A panic skips the end of any crew block the task’s body had open, so each task keeps a list of its open crews. A task that fails with crews open enters the unwinding state: the scheduler cancels their tasks, finishes the failed task once they have stopped, and frees the crews. Awaiters see the failure only then, so a crew’s tasks never outlive the frame they may borrow from.

A panic on a thread that is not a worker has nowhere to propagate, and that covers one rethrown into the entry function. exit_after_panic runs shutdown and then _Exit(101), so the entry function’s frame outlives its crews and no static destructor runs beside a worker.

Waiting on a word

std.sync builds its locks and channels on three calls that wait on a 64-bit word. wait_word(word, expected) blocks the calling thread while the word holds expected; on a worker it gives up the worker’s place like any other blocking wait. word_waiter(word, expected) returns a task that finishes once the word no longer holds expected, which a task awaits to suspend instead of block. wake_word(word) wakes every wait on the word. A wait re-reads the word under the scheduler’s lock and a wake takes the same lock, so a change followed by a wake cannot be missed. The waiters are kept in a table keyed by the word’s address. The calls are reached from Cinder as rt_word_wait, rt_word_waiter and rt_word_wake, together with rt_atomic_load, rt_atomic_store and rt_atomic_compare_exchange, which are sequentially consistent.

The io event loop

A task that waits for a file descriptor or a deadline waits in the reactor (src/runtime/reactor.{h,cpp}) and holds no thread. One reactor thread waits on the operating system’s readiness queue (kqueue on macOS and the BSDs, epoll on Linux) and on a heap of timers ordered by deadline. It starts on first use and lives for the rest of the process; its state is leaked on purpose, like the scheduler’s.

A waiter is a small native coroutine object, built the same way as a word waiter and spawned into the io pool at once. fd_waiter(fd, interest) finishes when the descriptor is ready to read or write, and timer_waiter(deadline) when the monotonic clock (monotonic_now) reaches the deadline. Its first poll registers it with the reactor and returns pending. The reactor marks a ready waiter in a stage word in its second value slot, outside the scheduler’s lock, and then wakes it with scheduler::wake, so its next poll returns done. The reactor never holds its own lock while it calls the scheduler. A wake that arrives while the first poll is still running is remembered by the scheduler, as for any other task.

  • Descriptors. Each descriptor has a list of read waiters and a list of write waiters. A registration is one-shot: an event takes every waiter in the direction it reports, and the descriptor is armed again only when a new waiter arrives. kqueue keeps the read and write filters apart. epoll keeps one registration per descriptor, which a one-shot event disables entirely, so the reactor re-arms it for the direction that still has waiters. An error or hang-up wakes waiters in both directions. A regular file, a directory, or a descriptor that is not open is never registered, and its waiter finishes on its first poll: such a descriptor never blocks, epoll refuses it, and kqueue would report an empty regular file as never readable.
  • Timers. A timer whose deadline has passed finishes on its first poll. An earlier timer than the one the reactor is waiting for writes a byte to a wake-up pipe the readiness queue also watches, so the wait ends and is recomputed. A timeout is rounded up to whole milliseconds for epoll, so a sleep never ends early.
  • Cancellation. A cancelled waiter is polled again by the scheduler and finishes. It stays in the reactor’s list until its descriptor’s next event or its deadline, when waking a finished task does nothing. The reactor holds the waiter while it is listed, so the stale entry cannot point at freed memory, and the waiter is freed once the reactor lets go.

The calls reach Cinder as rt_fd_readable, rt_fd_writable, rt_sleep_until and rt_monotonic_now, with rt_pipe, rt_set_nonblocking and rt_errno_would_block for setting up non-blocking descriptors. std.io’s async_file and std.time’s sleep are written in Cinder over them (std.io, std.time).

Process shutdown

shutdown cancels every unfinished task and waits up to one second for them to stop. It reports whether they all did, since a task that never reaches a cancellation check cannot be stopped. It runs at process exit through atexit, and cinder run calls it before freeing the VM and module; if a task is still running, the driver calls _Exit with the program’s status instead of freeing what the task reads. A task nobody awaited is therefore cancelled when the entry function returns.

Cancellation

cancel(task) marks a task the scheduler owns so that it unwinds. A queued task is flagged, a waiting task is flagged and queued, and a running task is flagged and handled when its step function returns. The flag is the same cancel_requested status a dropped generator sees, so the body runs its drops and returns at its next cancellation check. A cancelled task’s await cancels what it awaits and stays pending until that has stopped, so the check after it runs with nothing left borrowing from the frame. Cancelling a task also cancels the tasks of every crew it has open, at once, whichever await its body is at. A task the scheduler does not own is resumed by its dropper directly, as before.

The losers of a race are the exception: they are cancelled but not waited for.

Allocator

cinder_heap_alloc and its companions are safe to call from any thread. The system allocator inherits that from the C library; the arena allocator takes a lock around each bump.

Testing

reactor_test runs the event loop with one io worker: timers in deadline order, 100 timers waiting together, readers and writers on pipes and on one socket, hang-up, a full pipe, regular files and closed descriptors, and cancelled waiters. scheduler_test drives the scheduler with fake step functions, including 400 tasks on a four-worker pool, cancellation reaching awaited tasks and open crews, a panic in a crew body, and shutdown. allocator_test runs eight threads against the allocator, with the system and the arena allocator. Corpus files 150–153, 155–159 and 169–175 (on(cpu), race cancelling losers, crew, crew collecting errors, every exit from a crew body, async: blocks, borrows held across await, std.sync, suspending value branches, generic tasks, match subjects held across await, and sleeps and pipes in the event loop) run awaiting tasks, multiword results, par, race and a shared atomic counter on both backends, and the harness runs them with four io workers. Corpus files 178 and 179 loop over awaits, spawns, crew, par, race and dropped generators, and bound the heap blocks left behind with # max-live-blocks:. bazelisk test --config=tsan builds under ThreadSanitizer.
