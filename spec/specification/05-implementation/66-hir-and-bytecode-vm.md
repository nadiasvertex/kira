# 66. HIR and the Bytecode VM

**Status:** Implemented

The reference compiler's typed intermediate representation, the passes that run over it, and the bytecode compiler and virtual machine that execute it. The VM runs programs by default and runs all compile-time code.

## HIR

HIR (`src/hir/nodes.h`) is a typed tree. Every node carries a concrete type from the checker's type table, and every call names its target function or instance. By the time code is in HIR:

- generics are instantiated, so each instance is an ordinary function;
- operators, indexing, method calls and UFCS calls are direct calls;
- `for` loops over user iterators are desugared to `while let` over `next`;
- contract checks that were not proved are explicit nodes;
- drops are explicit calls at scope exits, with drop flags where a value is moved on only some paths;
- `try_from` proofs and `static for` unrolling have been expanded.

Lowering (`src/hir/lower.cpp`) reads the checker's results and never infers. It fails closed: an unsupported or not fully typed construct is a reported error, never a skipped function or placeholder.

In a task body, a suspension point has to be a statement. Lowering hoists each `await` in a statement into statements ahead of it. A loop whose condition awaits becomes `while true:` with the hoisted statements and an `if not cond: break` at its top. An `if` or `match` whose value is used and whose branches can suspend (an `await`, `?`, a `crew` exit, `par`, `race`) becomes a statement that assigns each branch's last expression to a hidden `<branch value>` local; that `hir_let` has no initializer and carries its type in `declared_type`. An `async:` block or `on(ctx):` body is lowered to a synthesized task function whose parameters are the outer locals it reads.

## HIR passes

These run once, before either backend:

- **Explicit references** (`reference_check.cpp`). Every borrow and dereference becomes an explicit node. A leftover implicit reference is reported as a lowering gap rather than compiled.
- **Tail calls** (`tail_calls.cpp`). Marks direct calls in tail position ([Tail-Call Optimization](../03-advanced/39-tail-call-optimization.md)).
- **Captures** (`captures.cpp`). Computes what each lambda captures and how.
- **Generator state** (`live_across_yield.cpp`). Finds the locals live across a `yield`; these form the generator's state block. `op_yield` stores the item in the object's value slot and returns `suspended`; `op_coroutine_resume` yields the step function's status, or the stored status if the coroutine already finished. A task's `await` is a `hir_yield` with `awaits` set: it polls the awaited task through the scheduler, and `op_await_pending` returns `pending` when that task is not finished. The state-block analysis treats it like any other suspension point. A local of a step function whose address is taken, or that a closure captures by reference (`captures.cpp`, `coroutine_borrowed_locals`), lives in its own state-block entry: its register holds that entry's address, as a promoted cell's register holds the cell's, and is never synced. A `&x` held across a suspension therefore does not point into a frame that has returned, and a `let` that runs again in a loop reuses the entry. A borrowed temporary, such as `await f(&xs[a..b])`, is one of these locals, because `make_references_explicit` stores every borrowed value that is not a place in a local first. The subject of a `match`, `while let` or `let ... else` is a local that every arm's bindings read, so it can be suspended state too; the step function writes the subject into the register a resumed poll reloads.
- **`or else`** (`lower_or_else` in `lower.cpp`). `x or else y` lowers to a two-arm `hir_match` on the operand, as `?` does. The success arm yields the payload. The failure arm yields the fallback, or holds the `return`, `break` or `continue` statement of a jump fallback. The ownership check records the `@err` payload drop in `unmatched_drops`, keyed by the AST node. Neither backend nor compile-time evaluation knows the form exists.
- **Frame budget** (`frame_budget.cpp`). Rejects a function whose stack-allocated buffers exceed the per-frame limit.
- **Reachability** (`link.cpp`). Finds every module the entry function reaches. A reached module is included in full.
- **Inlining** (`inline.cpp`). Replaces calls to small functions with a copy of the body. This is what makes standard library collections such as `list[T]` cost about what a built-in would. `--no-inline` turns it off.

## Bytecode compiler

The bytecode compiler (`src/bytecode_compiler/`) turns each HIR function into a flat instruction stream with its own constant pool. Code is emitted into an unbounded virtual register space, then a linear-scan register allocator maps virtual registers onto a frame's physical registers, reusing one as soon as its value dies. Parameters occupy the first registers; there is no separate locals area.

A second compiler, `storage_compile.{h,cpp}`, builds bytecode from the HIR storage form instead. In it a scalar, address, or handle that nothing takes the address of lives in a register. Every other value lives at a compile-time offset in the frame's byte storage (`bytecode_function::stack_byte_size`), which is 16-byte aligned, zeroed when the frame is created, and does not move when the frame vector grows. A parameter passed by address, and the hidden result, live in the caller's bytes, and the register holds the address. `bytecode_function::abi` records the sizes and classes so a host can call such a function with the right storage (`vm::run_into`, `vm::run_hosted_into`). Aggregates are moved with `op_copy_bytes`. `p[i]` on a raw pointer is `op_addr_indexed` followed by a load or store at offset 0; `op_addr_indexed` takes a one-byte element size, so a stride over 255 bytes is multiplied out first (with the VM's checked multiply, where LLVM wraps). The driver does not use this compiler yet; it is called only from its own test, because the two representations cannot meet in one program. A call to a runtime intrinsic is checked against the runtime symbol's shape (`hir::check_intrinsic_signature`). An intrinsic that returns an aggregate or `str` uses `op_call_intrinsic_into`, whose first argument register is the address of the destination; the handler calls the runtime's `cinder_rt_<name>_into` function, which writes every byte of the result and allocates only the data of a `str`. Other intrinsics use `op_call_intrinsic` and return in a register. `test_variant` loads the sum's tag word (`tag_offset` from the start of the sum) and compares it with the variant's tag by `op_eq` on `u64`. A `fn` value is three words `{entry, env, glue}` in the frame's bytes: the entry word is the function index, and the glue word is the index plus one, with zero meaning no glue. `op_make_closure` is not used; the compiler allocates the environment block with `op_alloc`, stores each capture at its offset, and stores the three words. A call through a `fn` value uses `op_call_function`, which takes the entry and passes the environment as the callee's register 0; a closure body reads its captures with loads at their offsets from that register. `op_drop_function_value` reads the glue word and calls the glue with the environment, and `release_environment` frees the block through `rt_free`. The older `op_call_indirect`, `op_make_closure`, and `op_drop_closure` serve the typed-HIR compilers. A generator is the runtime's eight-word object, built by `emit_make_generator` with `op_alloc` (the state block comes from the same allocator, so `scheduler::release` can free both). `generator_resume` is `op_coroutine_resume`; `take` loads the item address from the value word and copies the item from the state block; `dispatch` is a chain of `op_eq` and `op_jump_if_true` on the resume index; `suspend` stores the item address and resume index, returns the suspended status, and patches the dispatch jump for its point to the instruction that follows; `cancelled` and `finish` read and write the status word. Dropping a generator or task emits `op_coroutine_cancel` and then the `rt_task_release` intrinsic. A step's `coroutine_frame` slots are bytes of the state block, addressed from register 0. A task is the same object. `await #k` patches the dispatch jump for its point, stores the resume index, calls the `rt_task_await_poll` intrinsic with the task and the awaiting coroutine, and on a false result returns the `pending` status; otherwise it continues. In an ordinary function a task is read with `rt_task_block_on` followed by `take`. A group wait (`await all`/`await any`, and `block_on_group` outside a step) passes the runtime the address of the tuple of handles and its member count, so the tuple is a memory slot; `rt_task_await_all_poll`/`rt_task_await_any_poll` take the coroutine, the address, and the count, and `rt_task_block_on_all`/`rt_task_block_on_any` take the address and the count. A crew wait (`await crew`) polls `rt_crew_join_poll` with the coroutine and the crew handle, which is one register like a task's. `op_coroutine_has_item` is not an opcode: `has_item` loads the object's value word and compares it with zero, and `take` stores zero there after loading the item address, so the word marks an item that was handed over and not yet taken. A `string_literal` adds the bytes to the function's `string_constants`, loads their address with `op_str_const_data` (which, unlike `op_load_str_const`, allocates no header), and stores the length and the address into the descriptor's bytes. A descriptor's `length` and `data` places are its bytes at offsets 0 and 8. `checked_index` and `checked_end` compare two `u64` registers (`op_ge` or `op_gt`), panic with `index_out_of_bounds` through `op_panic_if`, and otherwise move the checked value to the destination. `replicate` doubles the written prefix of the array with `op_copy_bytes` at constant offsets, so an `n`-element fill takes about log2(n) copies and no loop. `compile_storage_module` takes a program of storage modules, the entry module first, and lays them out in one function table: an entry-module function is named plainly, any other module's `module::name` (`hir::program_function_name`), and a call into another module is an ordinary `op_call` on the index its owner's key resolves to. This compiler refuses by name `drop_in_place` of anything but a `fn` value, a generator, or a task, and 128-bit scalars.

## The VM

The VM (`src/bytecode/vm.cpp`) is a register machine.

- **Dispatch** is an ordinary `switch` over the opcode. Clarity takes priority over dispatch speed in this tier.
- **Frames** are an explicit vector, not C++ recursion, so Cinder's call-depth limit and its `stack_overflow` panic do not depend on the host stack.
- **Values** in registers are untagged slots; the compiler knows every type statically. Scalars live in the slot. Every other value lives in heap memory laid out by `src/runtime/layout.h`, the same layout the LLVM backend uses. A register is 16 bytes (`slot_value`), so an `int128`/`uint128` fits in one. Heap blocks keep 8-byte uniform slots (`heap_word`); in the uniform-slot shapes, such as sum payloads, a 128-bit value takes two consecutive slots (`runtime::slot_width`, `runtime::sum_payload_slot`).
- **Private blocks.** Closure environments, generator state blocks and promoted cells belong to the VM alone. Each entry is one whole 16-byte register image, so these blocks need no per-type layout.
- **Instructions** cover arithmetic in checked, wrapping and saturating forms; comparisons and casts; jumps; direct, indirect and tail calls; closures; generators and tasks (`op_make_generator`, `op_yield`, `op_await_pending`, `op_coroutine_resume`, `op_coroutine_cancel`); stack and heap allocation; slot and indexed loads and stores; address-of; panics; atomics; calls into runtime intrinsics; and host calls.
- **Runtime support** comes from `src/runtime/`: the allocator, string operations, formatting, platform queries and I/O. The VM calls these directly; compiled code links against the same library.
- **Panics** use one closed set of reasons shared with the LLVM backend, so both tiers fail the same way on overflow, division by zero, a failed contract, and similar conditions.

## Threads

`vm` holds only the module and the globals. Everything a run mutates, the call frames and the step counter, is local to one `execute` call, so one `vm` can run any number of executions on different threads. The task scheduler polls a task by calling `vm::poll_task`, which runs the task's step function in an execution of its own. A panic in it is thrown as `panic_error` and the scheduler records it as the task's failure. The globals table is the one piece of shared mutable state, and it is not locked: sharing data between tasks is governed by the language's rules for it ([Data-Race Freedom](../02-intermediate/30-data-race-freedom.md)), not by the VM. Code run at compile time cannot reach the scheduler; the task intrinsics are refused in a hosted run.

## Hosted runs

A hosted run supplies limits to the VM: a step budget, whether effects are allowed, and a callback for `op_host_call`. Compile-time execution uses a hosted run with effects off ([Compile-Time Execution in the Compiler](65-compile-time-execution-in-the-compiler.md)). A program run from the command line is not hosted.

## Use from the command line

`cinder FILE` compiles the program and runs its entry function on the VM. The VM is the reference tier: the test suite treats its results as the baseline the LLVM tier is compared against.
