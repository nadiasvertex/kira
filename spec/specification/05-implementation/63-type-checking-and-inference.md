# 63. Type Checking and Inference

**Status:** Implemented

How the reference compiler checks types: the checker's phases, the inference engine it is built on, how generics are checked and instantiated, and what the checker hands to later stages.

## The checker

The checker (`src/semantic/check*.cpp`) is one class that walks every module in a session. Its output, `checked_types`, is a set of side tables keyed by AST node: the type of every expression, the function or instance every call resolved to, operator and index dispatch, literal conversions, generic instances, elided checks, and drop plans. HIR lowering reads these tables; it never re-infers anything.

A session runs in this order:

1. Register `static def` functions and decide which bracketed parameters are bounded type parameters and which are value parameters.
2. Materialize parameterized-module (functor) instantiations, so the `impl`s and `extend`s they declare exist before the method table is built.
3. Build the method table and check impl coherence ([Coherence and the Orphan Rule](../02-intermediate/21-coherence-and-orphan-rule.md)).
4. Run item-level splices and `deriving` clauses. These execute compile-time code, which may check functions out of order; each `impl` they produce is added to the method table and coherence records as it is made.
5. Check functor bodies, then each file in turn. After each file, the generic instances that file asked for are made, so their diagnostics appear next to the code that caused them.
6. Make any remaining instances and settle any results still open.

A `for` loop's route is chosen from its iterable's type (`resolve_loop_route`): the borrowing `iter` or `iter_mut` for a written `&e` or `&mut e`, then a collection's `into_iter`, then the iterable's own `next`. When the iterable is a reference to a collection, `into_iter` would consume what the reference only borrows, so the loop takes the borrowing `iter` and copies each element out (`iterator_loop_dispatch::copy_elements`); `require_copied_elements` reports a loop whose elements are not `copy`.

A call is checked by finding its callee, then checking the arguments against that callee's signature. A free function written bare or module-qualified is found by `find_function_callee`, and one reached through UFCS (`x.f()`) by `try_ufcs_call`. A free function called with brackets (`zeros[8]()`, `pair[int32, str](a, b)`, `derive_show[point]()`) is found the same way, with the brackets as its explicit arguments (`infer_explicit_generic_call`); a `static def` takes the same path as any other generic function. A static member called on a type is found by `find_static_callee`: on an applied type (`list[int32].from_iter`), a prelude constructor (`option.pure`), a solved type parameter (`C.from_iter` once `C` is known), a builtin scalar (`int64.zero()`), or a bare type name, generic or not (`box.make(40)`, `point.make`). A method called on a value (`p.m(...)`) is found by `find_method_callee`, on a struct, sum, opaque or existential receiver, or through a builtin's impl or `extend` block; it also reports a refused `x.drop()`, a method that a `deref` step cannot reach, and a missing method. A method whose first parameter takes the receiver instead of `self` (a receiver-style method, `ma.bind(f)` under `impl monad for option`) is found by the same finder. A method or static reached through a bound on a type parameter (`x.cmp(y)` with `x: T`, or `T.zero()`, in a template) is found by `find_bound_callee`, among the traits the parameter's facts name; it reports a missing or ambiguous member. A call of a closure, a `fn`-typed local or field, or a generic lambda copy is a function-value call. Each finder describes what it found as a `call_callee` and hands it to `check_call`, the one call pipeline, which runs five stages. Stage 1 (`callee_signature`) reads the parameters under the callee's own file, with a member's block parameters in scope and bound from the type the static is called on or the receiver, so `wrap[int32].new(v)` and `w.set(v)` on a `wrap[int32]` take an `int32`. A self method's `self` is the receiver and is not among the parameters. A receiver-style method's receiver fills its first parameter: the block parameters are bound from the receiver as for a self method, and the method's own parameters the receiver mentions (`A` in `option[A]`) are kept apart from the block's, in `receiver_bindings`. A bound member's parameters are read under the trait's file with `self` standing for the type parameter, and the trait's parameters are bound from the fact's arguments (`K` is `int32` under `T: scale[int32]`). A function value's parameters come from its `fn` type and have no names or defaults. Stage 2 (`bind_explicit_args`) rejects brackets on a callee with no compile-time parameters. Stage 3 (`check_call_arguments`) checks the arguments and preconditions, and a receiver-style method's receiver ("for this method's receiver"). A function value's arguments are positional; a named one is refused ("`f` is a function value, so its arguments are positional"), and arity errors use the same wording as for a declaration, with a missing parameter numbered (`#2`). Every call except a refused one gets an argument mapping (`call_argument_mappings`), so an argument to a `&` parameter of a function value is lent, not moved. Stage 4 (`solve_call_callee`) solves the compile-time parameters: a free function's through `solve_generic_call`; a member's block parameters from the type or, for a bare generic name, from the arguments, then its own parameters, then the arguments against the solution and the bounds (`solve_member_callee`). A bound member is solved the same way with no block, so `T.conv[int64](v)` on a `static def conv[U](v: U) -> U` is an `int64` in the template, and the method's own bounds are checked there. Stage 5 (`name_call`) records the callee and names the instance: a free function's through `name_generic_call`, a static generic only through its block as `target::m$target` (`wrap::new$wrap_int32_`), and one with its own parameters as `target::m$args` (`wrap[int32]::ident$int64`). Self methods and receiver-style methods are named the same way, so `pick[U]` on a `bag[int32]` and on a `bag[int64]` are two instances. A function-value call has no callee record; the adapter calls the callee node's value. A bound member call has none either: which impl's method it reaches depends on the type parameter, so each instance names it. Operators, interpolation and `deref` steps reach the same naming stage (`instantiate_impl_method_for`, `name_member_instance`). A self or receiver-style method call keeps a callee record from the start, which the task carrier rule reads (`receiver_is_shared_borrow`). A template's call written in its own parameters, of any form, is named by each instance through one replay (`defer_call`, then `replay_call`). The replay rebuilds the callee on the instance's types: a self method and a bound member are looked up again on the instance's receiver, and a static or receiver-style method keeps its member with the target substituted. It then runs stages 1, 4 and 5 from the arguments' recorded types and checks nothing again. A free function is the same declaration in every instance, so its solution is the template's with the instance's answers substituted; a member is solved again, and its bounds are checked at the instance. Brackets are resolved where the template wrote them (`resolve_bracket_types`) and substituted at the replay, because an instance has no scope to read a template's `T` in. A call solved to an open leaf, including an open receiver (`xs.len()` on a `list[?a]`), is named once the leaf settles. A call to a `static def` from run-time code is run while checking and recorded as the literal it returned (`fold_static_call`, `folded_comptime_calls`); inside a block `static for` it is folded per iteration. A variant is looked up by `resolve_variant_value` for construction and by `check_constructor_pattern` for patterns, in the same order: the expected or subject type, the module's sum types, the prelude.

## The inference engine

Inference lives in `src/semantic/infer/` as a set of small, separately tested parts.

- **Metavariable store** (`infer_ctxt`). One union-find over type ids holds every unknown, whatever it ranges over: a type, a type constructor of known arity (the `F` in `functor[F]`), or a compile-time value (the `n` in `vec[T, n]`). Generic parameters, const generics, and higher-kinded heads therefore share one mechanism. The store also records a cause for each constraint.
- **Unifier** (`unify`). Applies three rules in order. Two rigid types unify structurally, and different constructors are a mismatch. A variable-headed application such as `F[A] ~ option[int32]` solves by matching the outermost nominal constructor, which keeps higher-kinded inference decidable with one most-general answer ([Higher-Kinded Traits](../03-advanced/37-higher-kinded-traits.md)). Value slots such as `vec[T, n + 1] ~ vec[T, 3]` go to the value solver. A constraint outside these rules is postponed, not failed, because its shape may still become known.
- **Value solver** (`value_solver`). Processes a linear equation, distinguishing flexible variables (the callee's `n`, which the call determines) from rigid ones (the caller's own `m`, fixed but unknown). So `n + 1 = m + 1` solves to `n := m`. The solver can determine one flexible variable; equations with several remain underdetermined unless refuted. GCD and sign checks supply refutations, not a complete decision procedure over nonnegative integers. See [Value-slot compatibility and inference](../03-advanced/33-dependent-and-refinement-types.md#value-slot-compatibility-and-inference) for the required acceptance rules and remaining conformance gaps.
- **Obligation queue** (`obligations`). Method resolution, trait selection and refinement narrowing are decisions that may need to wait until a type is known. They share one queue: each obligation is retried when something it depends on is solved, and reported if it never can be.
- **Blame** (`blame`). Constraints are kept after they are solved. When constraints disagree, blame chooses which one is the mistake by majority (four branches say `int32` and one says `str`, so the `str` branch is reported) and builds the message from the decisions that led there. A golden corpus of wrong programs (`src/testdata/inference_diagnostics/`) fixes the expected messages.

Integer and float literals start as open leaves and settle from the context that demands them. Demand is scoped: an operand of `==` or `<` ties to the other operand, but an expected type alone never forces a leaf.

A constructor's type parameters that its own parts do not fix are open leaves too (`checker::open_constructor_params`). A struct literal or a variant of a generic type opens each parameter its head leaves out as a leaf, and so do `@some`, `@none`, `@ok` and `@err` for a payload the expected type leaves open. The fields or payload solve what they can, and the context solves the rest where the value meets a declared type: `wrap { inner: it, last: @none }` returned as `wrap[I, T]` is recorded as `wrap[I, T]`, and `@none` passed as `option[T]` in `pick(@none, 4)` takes `int32` from the other argument. A parameter left as an unknown hole could never be solved, because the unifier does not bind a hole, and the recorded type would keep a `_`.

## Generics

A generic function is checked once, against its declared bounds ([Generics and Inference](../02-intermediate/19-generics-and-inference.md)). Inside the body, a type parameter is opaque except for what its `where` bounds and any enclosing `static if` provide. Bounds are enforced at each call site, so an error points at the call that violates them rather than inside the generic body.

One satisfaction query answers whether a type meets a trait or a concept (`checker::satisfies`). A bound is resolved into a `satisfaction_term` where it is written (`resolve_satisfaction_term`): the builtin `copy`, a trait with its arguments, or a concept. A bound at a call, an impl's own bounds, and `implements[T, C]()` (`fold_implements`) all ask it, so they agree. In a template, `implements[T, C]()` is folded per instance. Where a value meets a declared type (`type_mismatch`), value slots are compared with the enclosing generic declaration's value parameters held rigid (`value_slots_hold`), on top of `type_table::compatible`, which treats every value variable as solvable. A call's own value parameters are solved by `match_value_params` and stay flexible.

Each call names an instance: the template plus the concrete types and constants it was solved with (for example `get$3`). The instance queue (`instance_queue.cpp`) decides when each instance is made. Most are made by substitution: the instance copies the template's checked records with its parameters replaced, and replays only the decisions that depended on a type parameter (`instance_substitution.cpp`). Each backend then compiles every instance as an ordinary concrete function. There is no runtime polymorphism for generics; `box[trait]` and trait objects are the explicit exception ([Trait Objects](../02-intermediate/24-trait-objects.md)).

A trait default that an impl does not override is copied for that impl and checked with `self` as the impl's target (`checker::monomorphize_trait_default`). For a generic impl the copy is a template over the impl's parameters, checked under them and their `where` clause as the impl's written methods are. A call through a concrete receiver names an instance of it by the same rule as for a written method of a generic impl: `filter_iter::size_hint$` followed by the receiver's mangled type. A copy for an impl with no parameters is an ordinary function.

An impl may target a type with no declaration: a builtin scalar, a prelude generic such as `option[T]`, a tuple, or an array. Its methods go in a table keyed by the type's name (`impl_by_builtin`), shared by every tuple and every array, and lookup keeps only the impls whose target has the receiver's shape (`method_resolver::resolve_builtin_impl`). Coherence keys a tuple by its length, so a pair's impl and a triple's do not overlap. A generic impl of this kind is instantiated per receiver type like any other. `==` on a tuple, array, `option` or `result` is dispatched to its `eq` impl in `std.traits` (`checker::require_structural_operator`). Such a type has the trait only when the impl's bounds hold for what it holds (`checker::unmet_impl_bound`), and a failure names the element type at the operator or the call ([Equality on tuples, arrays, `option` and `result`](../02-intermediate/20-operator-overloading.md#equality-on-tuples-arrays-option-and-result)).

## Stability checks

`snapshot.cpp` renders every elaboration decision in `checked_types` as stable text ordered by source position. A test diffs this snapshot, so a change that silently resolves a call to a different instance is caught even when every program still compiles.
