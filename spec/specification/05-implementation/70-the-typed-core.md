# 70. The Typed Core

**Status:** Partial

A second representation of a checked program, the typed core, is built for every program, and HIR lowering reads it instead of the AST. The ownership check still reads the AST and the checker's side tables, and the drop schedule lowering uses is built from them. The core is a program in which nothing is implicit. A verifier re-checks it without inference, and a temporary adapter builds it from the checker's output. The tests run the whole pipeline over the standard library and the test corpus. For current coverage and the remaining phases, see `spec/unified-checker-plan.md` and the output of `//src:core_corpus_test`.

## Purpose

The core sits between the checker and HIR lowering and has one job: to say everything the checker decided, so that a later stage can read it without inferring anything again. Today those decisions are spread over side tables keyed by AST node (see [Type Checking and Inference](63-type-checking-and-inference.md)), and HIR lowering combines them with the AST. The core puts them in one tree (`src/core/nodes.h`):

- Every expression has a settled type.
- A place is a root (a local, a `static`, or a temporary) plus a list of projections: field, tuple element, variant payload, dereference, and builtin element. Indexing or dereferencing a user type is a call to its impl, followed by a dereference of the returned reference.
- A place is read, written, or borrowed only through `use` (a copy or a move), `borrow` (shared or mutable, written or inserted), and `assign`. There is no implicit borrow or dereference.
- There is one `call` form. Its callee names a declared function or an instance of one, a function or closure value, an intrinsic, or a trait method called through a bound (`trait_method`, with the bound's type as `self_type` and the trait's arguments as `trait_args`). Inside a template, a call to a template (the template itself included) names that template with its arguments in the caller's parameters, and its signature is the template's under them. Operators on user types, method calls, conversions, default arguments, and `for` loops over iterators are calls. Builtin scalar operators are `primitive` nodes.
- There is one `match` form: a subject place and arms, where each arm has tests (a structural description of the value) and bindings (each a projection of the subject, as a copy, a move, or an alias). `if let`, `let ... else`, and destructuring `let` elaborate to it.
- There is one loop, `while_loop`. A `for` loop is a `let` of its state followed by that loop.
- A function keeps its type and value parameters. An instance is a function whose `instance_of` points at its template.

The core does not say where values are dropped and does not fix a layout. The ownership check and HIR lowering decide those.

## The verifier

The verifier (`src/core/verify.h`, `verify.cpp`) is a type checker for the core with no inference. It trusts no decision made upstream: it recomputes each fact from the core, the type table, the member types in `checked_types::shapes`, and `checked_types::is_copy`. Type equality is equality of `type_id`.

Every rule has an id, listed with its statement in `verify.h`, and has a passing and a failing case in `src/core/verify_test.cpp`. The groups are:

- **T**, types: every type is settled, free of refinements and existentials, and mentions a type parameter only inside a function that lists it.
- **P**, places: roots are in scope, each projection is valid for the type before it, and writability follows from the root and path alone.
- **A**, access: a `use` is a copy exactly when its type is `copy`, a move leaves no reference or element behind, and a mutable borrow is of a writable place.
- **C**, calls: one argument per parameter, each of the parameter's type; the callee form is consistent with its declaration, value, or intrinsic name; generic arguments are settled and, for a callee whose template is in the program, as many as the template has parameters. A template callee's signature is the template's under its arguments (C2), and only a function with generic parameters may call a declaration the program holds only as a template (C10), since lowering cannot call one. A `trait_method` callee names a method of `checked_types::trait_method_signatures`, and its signature and receiver are the table's under `[self_type, trait_args..., generic_args...]` (C9).
- **E**, expressions: literals, primitives, casts, aggregates, blocks, `if`, `match`, lambdas, and `await` have the types their parts imply.
- **S**, statements: `let`, assignment, loops, jumps, and contract checks.
- **F**, functions: each symbol is introduced once, the body has the function's type, and a static's value has the static's type.

A violation is an internal compiler error, never a user diagnostic. The verifier does not yet check that a generic call's arguments meet the callee's bounds, including that a `trait_method` callee's `self_type` is bound by the trait, and it does not check that a `match` is exhaustive.

The compiler's own operations are the `intrinsic` callees whose names the elaborator chooses (builtin addressing, views, raw pointers, layout queries, string iteration, task forms such as `task_block`, `on_cpu` and `task_yield`). `src/core/intrinsics.h` holds the table: each name has a fixed shape for its signature and generic arguments, and rule C5 checks a call against it. An intrinsic name outside the table must be declared by an `intrinsic def` in the program.

## The adapter

The adapter (`src/core/adapter.h` and the `adapter_*.cpp` files, split by construct: expressions, statements, patterns, loops, lambdas, contracts, interpolation, static items, tasks) builds the core from the AST and the checker's side tables while the checker still writes them. It decides nothing. Each type, callee, conversion, and dispatch comes from a record in `checked_types`. It interns the reference and function types that the core makes explicit, and one more: the `option[T]` a `for` over a generator tests each `next()` result with, whose shape it adds to `checked_types::shapes` when the checker has not interned that type.

A place is built by `body_builder::place_of` with a `place_access`. A place that is written or mutably borrowed (an assignment target, the operand of `&mut`, a `&mut` argument, a `&mut self` receiver, and every place one of these is built on) is built with `mutate`; any other with `read`. The access matters only for an index of a user collection: a read is `at(v, i)`, or `*at_ref(&v, i)` when the element is not `copy`, and a written place is `*at_mut(&mut v, i)`, whose receiver is itself built with `mutate`. The checker records the `at_mut` dispatch beside every read of a user collection that has an `index_mut` impl, since only the context says which one a place needs. `v[i] = x` is a call to `set_at`; `v[i] op= x` writes the element in place through `at_mut`.

When a record is missing, or a construct has no core form yet, the adapter reports a `gap` that names the construct and the function, and leaves that function out. A gap the program causes by using a feature the compiler does not build yet has `gap::feature` set, and its `detail` is the message the user sees, the program's author can act on. The adapter makes these with `fail_feature`, and core lowering makes the same kind of refusal with `refuse_feature`, which fills `unsupported::message`. Every other gap, and every other refusal in core lowering, is the compiler's own: the driver reports it as an internal compiler error that names the item and the construct and says it is a bug in the compiler, not in the program. Core lowering never aborts on a malformed tree; it refuses it the same way. The verifier checks only the functions that were built. The adapter is temporary: the plan replaces it, and the side tables it reads, with a checker that emits the core directly.

Each node built from the AST keeps its `origin`, the key the drop schedule and the ownership check name it by, which is valid only while the AST is alive. For most nodes it is the AST node. For a block it is the address of the AST statement list the block was built from, which is how the ownership check names a scope. When one AST node becomes several core nodes, the one that plays its role for drops carries it: the jump of a `return`, `break` or `continue`, the `assign` of an assignment, the `let` of a `let` or `var`, the `let` of a `where` binding (`let::binding_origin` is the binding). A comprehension clause's loop body is a block whose origin is the clause, the scope the drop schedule ends each iteration's bindings in. A parameter written as a pattern is a parameter named `<param i>` whose origin is the pattern; the function body is a `let_pattern` match on it that binds the parts, and lowering puts the body in the parameters' scope so the parts are dropped at the function's end. Each core statement after the first that an AST statement becomes is marked `continues_statement`, so its temporaries end with that statement's.

## Running and testing

The core is built in every compilation that lowers from it, which is the default, after the ownership check and only if checking reported no errors (`src/driver/driver.cpp`). It is verified when `cli_config::core_check` is set, or when the environment variable `CINDER_CORE_VERIFY` is defined. There is no command-line option for either. The verifier's result is stored in `compile_report::core`: the functions built (and which of them are generic templates), the gaps, and the violations. Nothing in the report changes the exit status or the diagnostics.

Three tests cover it:

- `//src/core:verify_test` builds small cores by hand and checks that each rule accepts a correct program and rejects a broken one with the right id.
- `//src/core:adapter_test` checks the shape of the core built for each mapping rule of the adapter.
- `//src:core_corpus_test` compiles every program in `src/testdata/codegen_stress/` with the standard library, each in its own child process so that a crash is an observation. It de-duplicates functions by module and name, then prints the functions built, a histogram of gaps by construct, and the violations by rule. It fails when the number of functions built falls below a floor, when a program produces no observation, and when the verifier reports a violation that is not in `src/testdata/core_known_violations.txt`. The floor is raised as the adapter covers more. Setting `CORE_CORPUS_GAPS` prints each gap.

The allow-list has one entry per line: a rule id, a module, a function, and a comment giving the reason. A trailing `*` on a module or function matches by prefix. An entry is removed once the violation is fixed.

## Lowering from the core

HIR lowering reads the core, and nothing else of the program's source. `hir::lower_core_function` (`src/hir/lower_core_lowerer.h`, with one method per core node kind in `lower_core_*.cpp`) lowers one function from its core tree and `checked_types`. From `checked_types` it reads the type table, `shapes` and `open_shapes`, drop plans (`drop.drop_plans`, also for `needs_drop`), and the drop schedule (`hir::compute_drop_schedule`), which is built from the ownership CFGs and capture facts and also carries the copies of a generic lambda (`drop_schedule::generic_lambda_copies`). Whether a callee or a function consumes its receiver is the core's `receiver_mode`; the drop emitter no longer looks it up. It no longer reads `node_types` or `inferred_return_types`. It uses `origin` and `function::decl` only as lookup keys; it neither includes `parser/ast.h` nor reads an AST node. The facts lowering once read from the AST are fields of the core, filled by the adapter: a function's `declared_name`, `expression_body`, the coroutine `start` key and the consuming `receiver_type`; a parameter's `span`; `if_expr::tail_statement` and `match_expr::tail_statement` for a block's tail `if` or `match` statement; `assign::compound` for `a op= b`; `lambda::task_start` for a task block; and `call::context_origin` for the wrapper task of `on(ctx, t)`. The drop plan of a type with its own `drop` carries the function's name (`drop_plan::own_drop_name`, filled by the checker's drop planner from the declaration), so lowering reads no declaration. The reference pass lowering runs on each function (`make_references_explicit`, `src/hir/reference_check.cpp`) reads only the type table: a direct call's parameter types come from the core callee's substituted signature (`hir_call::target_signature`), and the drop emitter builds one for a type's own `drop`. Lowering returns `unsupported` for a construct it does not build: with a message when the program uses a feature the compiler does not build yet, and otherwise as an internal compiler error.

HIR lowering reads only the core and the checker's results it is keyed to. It covers scalar code, places, aggregates, direct calls, consuming receivers, the layout and container intrinsics, and drops: scope exits, early exits, assignment drops, drop flags and temporaries. The drops come from the drop schedule (`hir::compute_drop_schedule`, built from the ownership check's graph of the declaration), looked up by each core node's `origin`, and are emitted by `hir::drop_emitter` (`src/hir/drop_emission.h`). A binding's schedule key is `let::binding_origin` (the binding pattern, the `var` statement, or a `for` loop's iterable for its iterator) and a parameter's is `param::origin`.

`match_expr` carries the surface form it was elaborated from (`match_form`: `match`, `if let`, `while let`, a pattern `let`, `or else`, `?`, and the three `for` loop shapes), the AST subject as `subject_origin`, and how many dereferences the elaboration added to the subject (`subject_derefs`). Arms and pattern tests carry their AST patterns as `origin`, which is how the drop schedule's per-arm keys (owning subjects, unmatched and leftover drops) are found. A `for` loop's `while_loop` origin is the `for` statement or comprehension clause, and its block's origin is the iterable. `lower_core_match.cpp` uses these to build HIR's shapes: `hir_match` over a named subject local, `hir_let_else`, `hir_while_let`, and loop variables spliced into the enclosing block. A consumed `self` is the value in the core; HIR passes its reference, so each use reads through it. `lower_core_lambda.cpp` lowers lambdas with their capture lists and closure drop glue: a `lambda` records whether its captures are the source's own list (`capture_list`) and the AST lambda the drop schedule keys its captures by (`closure_origin`), and each `param` carries its binding pattern as `origin`. Generators and the bodies of `async def` functions lower with their cancel checks (`lower_core_task.cpp`); a `yield` statement's `jump::suspension` is the AST `yield` expression, which keys the drops of a generator dropped while suspended there. `lower_core_contract.cpp` lowers `contract_check`, whose `kind` says which clause it checks, and builds the exits: a `return` through postconditions or crew ends, and a function body's tail, which returns through the postconditions after the body's drops. Indexing with an inclusive range uses the `range_view_inclusive` intrinsic, which takes the last index rather than one past it.

An arm's pattern becomes one `pattern_alternative` for each alternative of a top-level `|`. A `|` below the top of the pattern is expanded the same way (`body_builder::alternatives_of` in `adapter_pattern.cpp`): the arm gets one alternative for each combination of choices at its nested `|`s, the product of the choices at each position, in source order with the leftmost varying slowest. Each alternative has its own test tree and bindings, and a name bound in several alternatives is one symbol. An arm that would expand to more than 64 alternatives is a feature gap reported to the user. The expansion makes no decision: the checker has already typed each alternative and its bindings.

Tasks lower in `lower_core_task.cpp`. In a task, each suspension (an `await`, a `?`, a crew that ends, a `par` or `race`) is placed ahead of its statement: `core_lowerer::hoist_` collects those statements while one statement lowers, and a branch that produces a value and may suspend assigns a `<branch value>` local instead. A suspension in a place that cannot go first (the right side of `&&` or `||`, a later `elif` condition, a guard, or a loop condition outside a task) falls back. A task block lowers to a nested function named `<task block FN@start>` and an `on(...)` to a wrapper named `<on FN@start>`, which the module holds beside the function that made it. An `on(ctx): body` block not awaited where it is written is the same wrapper as a value, a task that starts when it is first awaited. `await yield` is the intrinsic `task_yield`: in a task it lowers to a `hir_yield` with `awaits` set and no value, followed by the cancel check every `await` has; outside a task (the entry `async def main`) it lowers to nothing. The adapter refuses it outside an `async def` or a task block. A crew is the block `{ let k = crew_new(); body; crew_end(k) }`, whose `origin` is the crew statement or expression. Whether `crew_end` joins or yields depends on whether it is in a task, and a cancel check ends every open crew before it returns. `crew_errors[task](&k, new, push)` names the functions the checker chose to make and fill the list.

The adapter takes `core::adapt_options`. With `contract_checks` off it leaves out every `contract_check` and the `let return` and `let self` bindings they read, and the driver passes the same setting it gives lowering. A trait default the checker copied for a generic impl is a template in the core, as the impl's written methods are, and each call names one of its instances. A `for` over a borrowed collection whose consuming `into_iter` the checker allows (todo 39: the elements are `copy`) is `into_iter(bitwise_copy(xs))` in the core. `bitwise_copy[T](&T) -> T` duplicates the referent's bytes without making a second owner; it exists only for this loop and is removed in phase 7 of the unified checker plan. Lowering maps it back to the call on the reference, marked `receiver_borrowed`, and the iterator is not dropped. The failure arm of a `?` makes the value it hands back after the crews it leaves end and the drops run. The core checks postconditions at a `?` exit, as the specification (chapter 34) checks a `post` at each exit. A read of a reified static that the ownership check records as owned (`function_cfg::owned_static_reads`, which the adapter loads with the capture records from `build_function_cfgs`) is the static's value expression built again at the read, as a temporary; any other non-`copy` read is too, and a `copy` read is a `use` of the `global` place.

`hir::lower_core_program` (`lower_core_module.cpp`) builds whole modules from the core: each core module's functions in the adapter's order, then the functions its task blocks made, and its statics (`lower_core_static`). A module with a function the adapter left out (`core::gap::item` says whether a gap is a function, a static or an `intrinsic def`) or a construct the lowering does not support is not made, and the driver reports it as a lowering failure of that module: a feature gap as a feature the compiler does not build yet, anything else as an internal compiler error.

Lowering has one entry point for a whole program, `hir::lower_program` (`lower_core.h`): it runs `core::adapt_program` and then `lower_core_program`, and returns the core with the HIR modules and the failures. The driver, the codegen corpus (`src/codegen_corpus.cpp`) and the test fixtures (`lower_test_program` in `src/testing/stdlib_fixtures.h`) all lower through it. `CINDER_CORE_VERIFY` verifies the core of every program built this way, and of every program the compile-time VM assembles. In `lower_program` each violation becomes a lowering failure, reported as an internal compiler error, except those on a short list of known violations, each of which names the todo item that removes it. Every test target that compiles programs sets the variable.

## Compile-time code from the core

Compile-time code is built by the adapter and lowered from the core too. The compile-time VM (`src/comptime_vm/program.cpp`) lowers on demand, so the adapter has three entry points that use the same per-construct code as `adapt_program`: `core::adapt_function` (one declaration, under a name and module), `core::adapt_expression` (a compile-time expression as a function of its own: its captures are by-value parameters, its value is the body's result, and nothing is dropped) and `core::adapt_static` (one reified static's value). `adapt_intrinsic` gives an `intrinsic def`'s declaration. Every call to a free function has a callee record, and a call to an instance carries the generic arguments it was made with (`ownership_results::instance_generic_args`). The one name the adapter still looks up through `core::function_lookup` is a `std.fmt` helper that interpolation calls; in `adapt_program` that is the program index, and on the VM it is `comptime_program::find_function`, which also prepares the callee so its signature reaches the lowering view.

A function the VM runs has `function::compile_time` set: a module-level `static def`, a compile-time expression's function, and anything adapted with `adapt_options::compile_time`. Only such a function may hold a `host_call` (rule E12): the operations only the compiler performs, `quote` (subject the AST quote, arguments the splices it resolves while evaluated), `static` (subject the `static` declaration of a fragment-valued static) and `expr.<builder>` (no subject, the builder's arguments). It maps one to one onto `hir_host_call`. Outside compile-time code these constructs stay gaps. Every static read in a compile-time expression builds the static's value again.

`hir::lower_core_comptime_function` lowers either kind of function; one with no declaration is an expression's. `comptime_vm::comptime_lowering` carries whether to verify the core, which `vm_backend` reads from the environment. A feature gap is reported with its message; any other gap or unsupported node is reported as an internal compiler error with the construct and span. With `CINDER_CORE_VERIFY` the core of each program the VM assembles is verified as one program (its functions grouped by module, the statics it read, and the `intrinsic def`s it calls), and a violation is reported the same way. `CINDER_COMPTIME_VERIFY` lowers each function again from the final results through the same path; the bare names the first lowering looked up are kept, because the final results hold no program index. `CINDER_COMPTIME_CORE_LOG=<file>` appends one line per function, expression and static built this way, with the reason for a failure.

## Open shapes

`checked_types::open_shapes` holds the member types of struct and sum types that mention a generic parameter, such as `pair[T]` inside a generic body, expressed in terms of those parameters. It is kept apart from `shapes` because no layout exists for such a type. Only the core reads it: the adapter, to build field and payload projections in templates, and the verifier, to check them.

## Template callees

Inside a template, the checker records a call to a template with the callee's arguments (`resolved_callee::template_args`), in the order of the callee's core `generic_params`: the enclosing block's parameters, then its own. They are written in the caller's parameters: `self.reserve(n)` in `extend[T] list[T]` records `[T]`, and `bag[T].width[int64]()` records `[T, int64]`. They are recorded where the call is named in the template (`name_generic_call`, `name_call`, and the open-receiver path of `name_member_solution`), and not for an implicit-generic callee, for a call whose arguments have not settled when it is named (`pick(x, 40)`, whose literal is still open), or for a call whose receiver is reached through `deref` steps the template did not record (see the `deref` entry below). An instance's copy of the record has none: the instance's replay names an instance of the callee, and checks in debug builds that its `instance_generic_args` are the template's arguments under the instance's answers. The adapter calls a template callee only when its arguments are recorded, and otherwise reports a gap.

## Trait method signatures

`checked_types::trait_method_signatures` holds each trait method's signature in the trait's own terms, keyed by the method's declaration: `self` is the type parameter `self`, the receiver is `&self`, `&mut self`, or (for `into_iterator`'s `into_iter`) `self` by value, and `generic_params` is `[self, the trait's parameters..., the method's own...]`. A method whose parameters or result mention an associated type (`self.item`) has no entry, nor does one with a default body and no written result type. Rule C9 reads it.

## Calls through a bound

Inside a template, a call through a bound (`x.next()` with `I: iterator[T]`, `T.zero()`) records the trait's method as its callee, with `resolved_callee::bound` holding the trait, the bound's subject (`self_type`) and the bound's trait arguments, and `template_args` holding the method's own arguments. `name_bound_call` writes the record before it defers the call to instances, and only when the method has a `trait_method_signatures` entry, its own arguments and the bound's have settled, and the receiver is not reached through `deref` steps the template did not record. The adapter builds a `trait_method` callee from it: the signature is the table's under `[self_type, trait_args..., generic_args...]` and the receiver mode is the table's. It leaves a wrong argument count for C9 to report. Core lowering refuses a `trait_method` callee, which only a template holds. An instance's copy of the template's records drops a bound record, since no instance calls the trait's method: the replay records the impl's method, as before.

The record changes what the ownership check sees in a template. The receiver is lent by the trait's declared mode, read from the table: `self` is a `&` borrow, `mut self` a two-phase `&mut`, and `into_iterator`'s `into_iter` moves it. Before the record, the receiver was only read, so a second consuming call, a `mut self` call on a `let`, and a `mut self` call while a `&` of the receiver was live were all accepted in templates. A task's carrier rule reads the receiver mode from the same table (`receiver_is_shared_borrow`), so an `async` method called through a bound is no longer refused as a hidden carrier.

## Dispatch records in templates

Inside a template, the dispatch tables record a template callee's arguments in `template_args`, as a call record does, so the adapter can call the template itself. `dispatch_template_args` computes them for a method found on a target that mentions a template parameter: the impl block's parameters are matched against the target, and the method's own arguments follow. The tables that use it are:

- index dispatch (`xs[i]` on a `list[T]` records `at` at `[T]`), in `dispatch_index`;
- list literals (`[x, x]` as a `list[T]` records `from_array` at `[T, 2]`), in `record_template_from_array`, with the literal's length bound to the method's constant parameter;
- `for` loops, where `iterator_loop_dispatch` gains `template_args` for `next` and `adapter_template_args` for `into_iter`, `iter` or `iter_mut`;
- `deref` steps through a handle whose type mentions a template parameter (`guard.push(v)` on a `mutex_guard[list[T]]`), in `resolve_handle_step`. The template records the steps (`deref_adjustments`, and `deref_mut_adjustments` or `path_deref_mut_adjustments` for a write) when every step has a callee, and a call on the handle's target then records its own arguments.

An instance's copy of these records clears `template_args` and `adapter_template_args`, since each instance names concrete callees by its own replay.
