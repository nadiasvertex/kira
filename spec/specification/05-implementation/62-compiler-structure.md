# 62. Compiler Structure

**Status:** Implemented

The layers of the reference compiler, in the order a compilation passes through them, and the data each layer hands to the next.

## Overview

The compiler is a single process that takes a set of source files and either runs a program on the bytecode VM or builds a native executable through LLVM. Between the source and either backend there are three representations: the AST, the checker's results (side tables keyed by AST node), and HIR, a typed tree that both backends consume.

```
source files
   │  parse (per file)
   ▼
AST ──► static-if import folding ──► module graph + name resolution
   │
   ▼
type checker ◄──► compile-time execution (HIR on the bytecode VM)
   │  checked results: types, resolved calls, instances, proofs, drop plans
   ▼
ownership check
   │
   ▼
HIR lowering ──► HIR passes (references, tail calls, inlining, ...)
   │
   ├──► bytecode compiler ──► bytecode VM            (cinder FILE)
   └──► LLVM codegen ──► object file ──► link        (cinder --compile FILE)
```

## Layers

1. **Driver** (`src/driver/`). Reads the command line, adds the standard library's `.cn` sources to the session, and runs each stage below. The standard library is compiled from source in every session, under the same rules as user code.
2. **Parser** (`src/parser/`). A hand-written lexer and recursive-descent parser produce one AST per file. The lexer synthesizes `INDENT`/`DEDENT`/`NEWLINE` tokens from indentation. The parser never stops at the first error; it inserts error nodes and resynchronizes, so later stages see a structurally valid tree.
3. **Import folding.** `static if` blocks that guard `use` declarations are evaluated before the module graph is built, so the selected imports become ordinary top-level items.
4. **Module graph and resolution** (`src/semantic/analysis.cpp`, `resolution.cpp`, `scopes.cpp`). Files are grouped into modules, module boundaries and imports are validated, and a scope tree and symbol table are built. Types, values, type parameters and associated types live in separate namespaces.
5. **Type checker** (`src/semantic/check*.cpp`, `src/semantic/infer/`). Resolves every name, infers and checks every expression's type, resolves every call to a specific function or instance, checks trait coherence and bounds, and discharges proof obligations. It runs compile-time code as it goes. See [Type Checking and Inference](63-type-checking-and-inference.md), [Proof Solving](64-proof-solving.md), and [Compile-Time Execution in the Compiler](65-compile-time-execution-in-the-compiler.md).
6. **Ownership check** (`src/semantic/ownership_check.cpp`, `ownership_cfg.cpp`). Builds a small control-flow graph of ownership events for each function and lambda body and enforces use-after-move, borrow exclusivity, and loan lifetimes without annotations ([Ownership and Borrowing](../02-intermediate/14-ownership-and-borrowing.md)). A `crew` body holds the borrows of every task spawned into it until the crew ends. It also rejects a write, `&mut`, `mut self` call, or move through a `static`, which it finds through the checker's `static_refs`, and a `&mut` or `mut self` call on a `let` binding or on a name a `match`, `if let`, `while let` or `for` pattern binds to a value it owns (the checker's `immutable_pattern_bindings`). The checker itself rejects assignments to them. Any write, `&mut`, or `mut self` call that reaches its target through a `&T`, a `*T`, or a shared view is rejected too; a `*mut` along the way makes what it points at writable again. Its maybe-moved facts also decide where drops and drop flags are needed.
7. **HIR lowering** (`src/hir/lower.cpp`). Turns each checked module into HIR: a tree in which every node carries a concrete type, every call names its target, and generics, operators, method calls, `for` loops, contracts, and drops have been made explicit. Lowering fails closed: a construct it cannot lower is reported, never skipped.
8. **HIR passes** (`src/hir/`). Make every borrow and dereference explicit, mark tail calls, compute lambda captures and generator state, check per-frame stack budgets, find the modules a program reaches, and inline small functions. These run once, before either backend, so both backends see the same program.
9. **Backends.** The bytecode compiler and VM ([HIR and the Bytecode VM](66-hir-and-bytecode-vm.md)) and LLVM code generation ([LLVM and Ahead-of-Time Compilation](67-llvm-and-aot.md)). Both read the same HIR and share heap layout rules from `src/runtime/layout.h`.

The checker also records the concrete fields of every struct instance and the concrete payloads of every sum instance (`checked_types::shapes`, `src/semantic/aggregate_shape.h`), with generic arguments substituted. `src/runtime/value_layout.h` computes byte layouts from them: inline members with offsets and padding, array strides, sum tag and payload offsets, and a diagnostic naming the field path of any type that contains itself by value. The backends do not read these layouts yet. They still use the pointer-per-aggregate rules in `layout.h`, and `size_of`/`align_of` still answer from it. Both models exist together while the backends migrate.

`src/hir/` also holds a storage form that states where each value lives: `storage.{h,cpp}` defines slots, places (a slot plus member, element, payload, dereference, or descriptor `length`/`data` projections), and the operations that build, copy, move, call into, and end them; `abi.{h,cpp}` classifies each type as zero-sized, scalar, address, handle, descriptor, or aggregate and derives internal signatures in which an aggregate result is written through a caller-supplied address; `storage_lower.{h,cpp}` lowers straight-line HIR into the form, forwarding destinations into constructors and calls; and `storage_verify.{h,cpp}` checks initialization, projections, transfers, storage lifetime, signature agreement, result completeness, and ownership. The form expresses `if`, `while`, `break`, `continue`, and early `return` as structured markers in a flat operation list (`if`/`else`/`end_if`, `loop`, `block`, `exit N`); the verifier joins initialization and drop state where paths meet and requires a loop body to end in the state it began with. A value moved on only some paths is governed by a drop flag (a `bool` frame local named `<drop flag>` that HIR writes): where one path holds the value and the other does not, the verifier keeps the value as maybe-held together with the flags whose constant values tell the paths apart, and an `if` on such a flag restores the held state on its `then` side and the empty state on the other. Writing a flag forgets what it told, a maybe-held value may not be overwritten or ended, and a return while one is still maybe-held is a leak. `never` has a zero-sized layout, and a call that returns it (`panic`) is followed by `unreachable`, which ends the path: the verifier accepts it only after such a call and checks nothing on the path past it, the bytecode compiler emits a panic there as a backstop, and LLVM emits `unreachable`. A branch whose value is `never` writes nothing to the destination the other branches write. The body's trailing expression statement is the value the function returns (HIR types a trailing `match` or `if` with the result type), lowered as a `return` of that expression, unless every path through it already leaves, in which case it stays the statement it is. The drop calls HIR synthesizes (`hir_call::is_drop`) stay calls on the address of a place; the verifier reads them against the checker's drop plans, so that each value's own drop and each droppable field's drop runs once, nothing is used after its drop, a replacement is written only after the old value's drops, and nothing droppable leaves its slot still owing a drop. Raw memory is expressed with a `pointer_offset` computation (`p + i * stride`, the stride being the element's size under the concrete layouts) followed by a dereference, so `p[i]` is a slot of inline bytes whatever the element type, and an array at a constant index is an `element` projection. Behind a raw pointer the verifier follows chapter 38 rather than the reference rules: a read moves or copies the value out and leaves the slot untracked, a write never drops the old value, and a drop call on a value there is accepted without tracking. An array whose elements need a drop is dropped by a loop HIR writes over a raw pointer to its first element (`container_data` with `takes_elements`), after which the array is given up by a `forget` operation, which the verifier treats like `drop_in_place` and the backends emit nothing for. `uninit` storage is zeroed by a `zero_fill` operation when it is made; the verifier allows it only on `uninit` and counts it as a write. A dereference of a `cell[T]` or `cell_mut[T]` reaches the `T` (`storage_env::pointee`). A function that owns its receiver (`hir_function::owns_receiver`: each `into_iterator` impl's `into_iter`) takes `self` as a `T` passed by address rather than as a `&T`, and the caller (`hir_call::receiver_by_value`) moves the receiver in. A `size_of` or `align_of` literal carries its question (`hir_literal::question`), and the storage lowerer asks it again of the concrete layouts, because HIR's own answer is for the legacy boxed aggregates. A lambda lowers to a `make_closure` operation that builds the `fn` value `{entry, env, glue}` in its destination, plus two more functions in the module: the body, which takes the environment as a hidden first operand and reads each capture from an environment slot at its byte offset (`env_indirect` when the capture is a reference), and, when the environment is not empty, drop glue that drops the owned captures in reverse capture order and then runs `release_environment` to free the block. A named function used as a value lowers the same way, with an empty environment and no glue: its entry is a forwarding function (`<enclosing>$fn<N>`, made once per function per module) whose body calls the named function with its own parameters and returns the result. A capture is a copy, a move, or a reference (`capture_kind`); the verifier refuses to move a value out of an environment slot, and checks capture offsets, alignment, and the signatures of the entry and the glue. A call through a `fn` value reads its entry and environment from the value's bytes, and `drop_in_place` of a `fn` value runs its glue. `match`, `while let`, and `let ... else` lower to `test_variant` operations (`dest <- source is @variant`, a `bool` read from a sum's tag) and ordinary comparisons, nested so that a payload or a literal is read only inside the branch that confirmed its variant. Each arm is a flag set by its tests and an `if` on that flag; the last arm of a `match` has no test, because the checker requires every value to be covered. A subject that is a local is used where it stands, a computed subject is built in its own slot, and a `while let` rebuilds its subject on every iteration and leaves the loop when the pattern fails. A binding is the `let` that HIR already placed in the arm, so it copies or moves the payload out of the sum's bytes; the verifier lets a payload leave a sum, and then the sum can no longer be read whole. A sum that needs a drop may lose a payload only where an `if` on its `test_variant` flag showed the variant (see below). Constructor, literal, tuple, struct, wildcard, and or-patterns are lowered. A sum that owes drops can be matched with wildcards, literals on scalar parts, tuple and struct patterns, and constructors nested to any depth (or-patterns and ranges are refused by name); each tag test is the `if` itself, not a flag set in nested branches, so the verifier can narrow the sum to the variant on each side. The sum tested may be a payload or member of another sum whose variant is already known, so the verifier narrows along a path: it splits each whole value on the way into its parts, narrows the inner sum, and still accepts a tag test of a sum so split. A match on a part of a value (HIR's drop glue for a sum nested in a sum) names that part through the subject's symbol. At a join, sums that differ only in the variants they may hold merge at any depth, and a sum that one path split and the other did not merges as a whole sum when the split one still has all its payloads; what the nested tests learned is forgotten and the tests after the join learn it again. A nested pattern has several places where a test can fail, and the lowering emits a copy of the failure path (the remaining arms, or the `else` block) at each. HIR already writes the drops of a sum as a `match` over its variants with `drop` calls on the payload places, and an arm that binds a payload moves it out and drops the rest, so no operation is added. Where two paths of a sum that owes drops meet, the variants it can still hold are merged, and a path that owes nothing on both sides leaves the slot empty. An arm may have a guard: the pattern is tested, the bindings HIR places ahead of the guard run, and the guard decides between the body and the remaining arms, which are built at both failure sites. A guard is refused when a binding needs a drop, or when HIR runs a drop (of a payload the pattern does not name) before the guard, because a failed guard must leave the subject whole. Any other pattern on a subject that needs a drop (a tuple, an or-pattern), range and array patterns, and string literal patterns are refused by name. A value is built where it ends up: constructors, tuple and array literals, sum payloads, `if` and `match` branches, blocks, calls (direct, indirect, and generic instances), `?`, and `or else` all receive the destination place, so none of them builds a temporary and moves it. An assignment is the exception: the replacement is built apart, the old value dropped, and the replacement moved in. The failure arm of `x?` returns the operand itself in HIR; when the operand type is not the function's result type (the success types differ), the lowering rebuilds the failing variant in the result from the operand's payload (`err`, or `none`). A part of a value under construction that needs a drop is noted once it is built (`partials_`), and a `return` inside the construction (the failure arm of a later `?`) drops those parts first, newest first; `break` and `continue` inside such a construction are refused. When a variant is published over leftovers of another variant (the parts a failed construction wrote before the failure arm wrote its own payload), the verifier drops those leftovers from its state if none of them owes a drop, and reports a leak otherwise. NRVO is a pass over each lowered function (`storage_nrvo.{h,cpp}`, on by default, off with `storage_lower_options{.nrvo = false}`). When every `return` of a function whose result is written through an address moves the same whole local into the result, the local's places become the result's, the moves and the local's `storage_dead` are removed, and its slot is deleted. The local qualifies when it is a `frame_local` of exactly the result type, holds no value on entry, is first written outside every `if` and loop, is moved only at the returns, has no address taken (a synthesized `drop` call excepted), and is not captured. A return that builds its value some other way, two different returned locals, a parameter, and a borrowed or captured local all keep the ordinary move. `storage_lowering::nrvo` records one decision per function with a returned local, with the reason when it was declined. The verifier's `normalize` drops stale member records under a whole value, so a loop that mutates a local built in the result compares equal at its ends. The frame check (`storage_frame.{h,cpp}`) runs last in `lower_to_storage`, after NRVO. `plan_frame` adds up the `frame_local` and `outgoing_argument` slots of nonzero size, each at its layout's alignment and in slot order; parameters, the caller's result, globals, owner fields, closure environments, and coroutine frames belong to other storage and add nothing. No two slots share bytes, so a loop cannot grow its frame. A function over `storage_lower_options::max_frame_bytes` (the 1 MiB `k_max_frame_stack_bytes` by default) is refused with `frame_too_large`; the message gives the total, the limit, and the three largest contributors, and the span is the largest one's. The arithmetic is checked and reports overflow rather than wrapping. `storage_lowering::frames` holds the plan of each function that lowered. The bytecode compiler keeps its own 32-bit frame-offset check as a second line of defense, and neither storage backend emits a tail call, so no frame is reused while a callee holds an address into it. A `generator def` lowers to two functions. The constructor is an ordinary function: a `make_generator` operation allocates the state block, copies or moves the parameters into it at the offsets the step assigned, builds the coroutine object (`runtime/coroutine.h`), and returns the handle. The step function `<name>$step` (`coroutine_step`) takes the state block as its environment and the resume index and coroutine as parameters. Every one of its slots, parameters and temporaries included, is a `coroutine_frame` slot at a fixed offset in the block, so a suspension saves and restores nothing and a borrow of a local stays valid. The step begins with `dispatch`, which jumps to the point after the suspension the resume index names (zero starts the body). `yield` becomes `suspend #k`, which consumes the item, stores its address in the object's value word, stores the resume index, and returns; each suspension is followed by `cancelled`, which tests for a cancel request and, if set, runs the body's unwinding to a `finish` and `return`. `finish` marks the coroutine done. `.next()` becomes `resume` (the step's status), a comparison with the suspended status, and then either `take` into the `@some` payload or a published `@none`. Dropping a generator is `drop_in_place` of the handle, which unwinds a suspended one and releases the object. The verifier requires each suspension point to be placed once, the dispatch to come first, step-only operations to appear only in a step, and the item type to match the generator's. A generator whose items need a drop can be defined but not read through `.next()`. An `async def` lowers the same way, as a task whose body is `yield result; return`; the scheduler treats a `suspended` status from a task as "result handed back" and finishes it. Inside a task, `await task` becomes `await #k`, a resume point that polls the awaited task (`rt_task_await_poll`) and, when it has not finished, stores the resume index and returns `pending`; the step resumes at the same `await` when the scheduler wakes it. The awaited task is a `coroutine_frame` slot, so it survives the suspension, and the step's cancel exit drops it before the other drops. After the wait the result is moved out with `take` and the task dropped. In an ordinary function, including the entry `async def main`, `await task` and `task.get()` call `rt_task_block_on` (on the io pool) and then `take`; `await` also drops the task. Calls to `rt_task_*` and `rt_crew_*` borrow their handle arguments. An intrinsic whose parameter is declared `&T` receives the address of the `T` in the storage form, although HIR passes `*x` there for the legacy boxed representation. A `yield` in a task builds its item at the task's item type (`T`, or `result[T, E]` when `E` is not `never`), so the failure arm of `?` rebuilds its operand at that type. The verifier requires an `await` to be in a step, to be placed once, to name a task as both awaiter and awaited, and to agree with the task's result type (`result[T, E]` when the error type is not `never`). `await par` and `await race` start each branch task, move the handles into one tuple local, and wait on the tuple as a whole: in a step, `await all #k` or `await any #k` (`wait_mode`) polls the tuple with `rt_task_await_all_poll` or `rt_task_await_any_poll`, which read its handles in place; in a plain function, `block_on_group all|any` blocks the thread (`rt_task_block_on_all` and `rt_task_block_on_any` calls are lowered to it). After the wait, each result is taken out through the tuple and each member dropped; a `race` also cancels the members first. The cancel exit of a group wait drops the members one by one, because the legacy lowering names each awaited task. An `on(pool)` block is a task of its own and lowers as any other task. A result that needs a drop is owned by whoever reads it. Dropping a task handle first drops an unread result: it calls `rt_task_is_finished` (a task still running owns its result, so an unfinished one is skipped), then `has_item` (a flag for an item that was handed over and not taken), then `take`s the item into a temporary and drops it with synthesized calls (the type's own `drop`, then each droppable field in declaration order, or each droppable tuple member). `take` clears the item flag, so a result that was read is not dropped twice. A result that is a sum with droppable payloads is dropped by a tag test per variant that owns drops, each directly in its `if`; a sum nested in another result, and a result whose drop is not modeled (a `result` from a fallible task, a closure, a generator), are refused by name at the handle's drop. A `crew` block is a `rt_crew_new` handle, a `rt_crew_spawn` per task, and a wait before `rt_crew_free`. `rt_crew_spawn(crew, task)` takes the task (the argument is moved) and returns the same handle, so only the crew itself is borrowed; a handle that is dropped while the crew runs leaves the task to the crew, since `drop_in_place` of a task uses `cancel_on_drop`. The wait is `await crew #k` in a step (`wait_mode::crew`, which polls `rt_crew_join_poll`) and `rt_crew_join` in a plain function. When the block's value is a task or a tuple of tasks, the cancel check after the wait releases those tasks, because no name owns them yet. A borrowed handle argument is read in place even when a later argument has effects. `c.errors()` is refused by name: it reads tasks the crew still owns. The ownership graph has a cancel point after a `crew` wait and after `t.get()` in a task, so the cancel exits HIR writes there drop what the task owns; `t.get()` on a local waits on the local itself rather than on a second name for it, and an `on(pool, task)` wrapper dropped before it runs releases the task it carries. A computed `match` subject ends before a `break` or `continue` leaves the loop it was made in, and a `while let` subject ends after its loop. A `str` literal is a `string_literal` operation: its decoded bytes are static data for the program's lifetime, and the operation writes the `{len, data}` descriptor into its destination, so no literal is ever allocated. A `str` or `slice` descriptor's two words are places of their own: `s.len` (a `usize`) and `s.data` (a raw pointer to the elements, `*byte` for a `str`), each projection carrying the type it is read as. `xs.len()` reads the length word (an array's count is a constant), `xs.as_ptr()` reads the data word or takes the address of an array, which the verifier accepts as a pointer to its elements, and `slice_from_raw_parts(p, n)` writes both words; the verifier counts a descriptor complete once both words are written. Indexing at a run-time index is a `checked_index` compute (the index against the length, both `usize`), a `pointer_offset` from the data word (or an array's address), and a place through the result; a constant index into an array stays an element projection. A range index checks `end <= len` and then `start <= end` with `checked_end` (an inclusive end is widened by one first) and writes the view's data and length words. `&mut xs[a..b]` is typed `&mut slice_mut[T]`, and on a type with its own `index_mut` (a `list`) it calls that method instead of slicing the value's bytes. The verifier requires an offset's stride to be the size of what its result points at. An element that needs a drop is refused at a run-time index, since reading it would move it out of the container. An array fill `[v; n]` builds `v` into element 0 and then a `replicate` operation copies element 0 over the rest; the verifier requires the source to be element 0 of the destination, written, and `copy`. A field, element, or constant index of a value that is not a place is read from a temporary built for the statement. A `while let` whose subject needs a drop (a `for` over values that need a drop arrives as one) tests the variants as a `let else` does and leaves the loop where the pattern fails. A reified static (an array, tuple, or `str`; HIR folds a struct static into its value) is a `global` slot. Each module that has statics gets a function named `static init` (`k_static_init_name`, which no source function can be named) that builds them, and the module lists them in `storage_module::globals`; a program runs each module's static init once, in module order, before anything else. The verifier lets only the static init write a `global` slot, which starts unwritten there and must be complete at its return; elsewhere it starts written and nothing moves out of it. Where paths meet, a structure or tuple that owes drops settles member by member, so a struct whose optional fields are each dropped under their own `if` joins cleanly, and a part whose variants a test narrowed is not folded back into a whole value. A variable read through `ptr_cast`, which has no HIR node, is copied into a temporary of the cast pointer type. The address of a `T` may be typed `cell[T]` or `cell_mut[T]`. An `uninit[T, N]` buffer is indexed like an array, but every index, constant or not, is checked against `N` and reaches its slot through the buffer's address, so the slot is raw memory under the chapter 38 rules. `c.set(v)` on a `cell_mut[T]` (`hir_cell_set`) is an assignment through the cell's address; a cell whose element needs a drop is refused by name, because HIR stages no drop of the old value there. A task block's capture that the task only borrows (`hir_param::lent`, listed in `hir_call::lent_args`) and that is not `copy` is passed as a shallow copy, and the constructor's parameter and the state-block slot that hold it own nothing (`storage_slot::owns_nothing`), so the owner keeps the value and the task never drops it. Moving a value out through a raw pointer leaves the pointer itself as it was. Indexing other than the two above is refused by name. `and` and `or` lower to a conditional, so the right side runs only when the left does not decide the result. The bytecode compiler's `storage_compile.{h,cpp}` (chapter 66) and the LLVM compiler's `storage_codegen.{h,cpp}` (chapter 67) read the form, but the driver uses neither yet. Each takes a program of several storage modules, the entry module first, and compiles them into one unit with one function table: an entry-module function is named plainly and any other module's function `module::name` (`program_function_name`), so modules may share a function's name. A call names its callee's owner module (`call_target::owner_module`, from `hir_local_ref::owner_module`), or none for a function of its own module, and `program_callee_name` turns that into the table key; the drop calls HIR synthesizes carry the owner of the type's `impl drop`. The verifier checks a call into another module against that module's function when `verify_options::program` lists it, and takes it on trust otherwise. `hir/intrinsic_abi.{h,cpp}` holds the check that a call to a runtime intrinsic agrees with the runtime symbol (`src/intrinsics.h` marks which symbols build their result in caller storage; `src/runtime/result_out.h` has the layout constants those `_into` functions write). The tests of both share `src/testing/storage_fixture.h` (a program lowered and verified; a fixture names companion modules with `# with: <file>` lines) and `storage_cases.h`, `storage_intrinsic_cases.h`, `storage_memory_cases.h`, and `storage_module_cases.h` (value, intrinsic, raw-memory, and cross-module cases with hand-computed expectations).

## Cross-cutting rules

- **Errors stop execution, not analysis.** A file with a parse error is skipped by later semantic stages so one mistake does not produce a cascade. A program with any error is never run or linked.
- **Diagnostics are part of the output.** Every stage reports what it expected, what it found, and how to fix it. Inference failures are explained from a retained record of constraints, not from whichever constraint failed last.
- **Whole-module compilation.** A module the program reaches is compiled in full, not only the functions it calls.
- **Module metadata.** After checking, the driver writes protobuf metadata for each module (`src/module_metadata.proto`) under `cinder-out/module-metadata/`, or the directory given by `--metadata-dir`.
- **One semantics, two executors.** Run-time and compile-time code both execute as HIR. The language's behavior is implemented once in lowering and twice in the backends, and the test suite cross-checks the two backends against each other and against expected values.
