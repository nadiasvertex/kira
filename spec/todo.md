1. Unicode locale-tailored casing (Turkish/Azeri, Lithuanian — needs a locale parameter threaded through every casing call), NFC/NFD normalization, and grapheme-cluster segmentation (UAX #29) so `reversed`/`split` operate on graphemes rather than scalars.
2. "with" style scoped blocks.
3. Store and load binary AST instead of reparsing.
4. Store and load generated bytecode instead of recompiling.
5. `float128` has no representation on either backend, so it has no `zero`/`one`/`hash`/scalar trait impls and no `std.limits` answers. A reachable module is compiled in full, so an impl naming it would break every program. It needs a soft-float implementation: LLVM's `fp128` lowers to compiler-rt/libgcc calls, and Apple arm64 has no `fp128` support at all, so the runtime has to supply the arithmetic itself.
6. Resolved; confirmed 2026-11-15. `std.limits.min[int64]()`, `min[int32]()`, and `min[int128]()` evaluate to the right values at compile time and at run time. Corpus `206_limits_min_values` checks all three with `# expect:`.
7. Resolved; confirmed 2026-11-15. A `static pure def` from `std.limits` called in ordinary run-time code compiles and runs on both tiers. Corpus `207_limits_min_in_run_time_code`.
8. A module-qualified call with explicit type arguments does not bind them: `use std.limits` then `limits.max[int32]()` reports "cannot tell what `T` is in this call to `max`". `use std.limits.max` then `max[int32]()` works.
9. A trait's static method called directly on a builtin type fails at code generation: `int64.zero()` (with `use std.traits.zero`) reports "no concrete checked type is available for this node". The same call through a bound (`T.zero()` with `T: zero`) works.
10. On Linux x86-64, `int128` checked multiplication may lower to a call to `__muloti4`, which libgcc does not provide. Untested; macOS links it from compiler-rt.
11. Resolved; confirmed 2026-11-15. `*p += x` and `*p *= 2` with `p: &mut int32` work on both tiers, directly and in a function that takes the reference. Corpus `208_compound_assign_through_mut_ref`. Compound assignment to a list element is still open (item 37), and item 12 fails for its own reason.
12. There is no mutable deref trait, so `*guard += 1` on a `mutex_guard` (chapter 30's example) cannot compile. `std.sync` guards offer `get_mut()` and `set(value)` instead.
13. Not reproduced 2026-11-15. A task that owns a list, wrapped with `on(cpu, t)` and dropped without being awaited, leaves no live blocks: corpus `209_dropped_on_value_frees_captures` requires `# max-live-blocks: 0`, and `leaks --atExit` on native builds of five shapes reported none. The block form `on(ctx): body` bound to a name could not be tested, because it does not lower (item 36).
14. `implements[T, copy]` cannot be used, because `copy` is a concept rather than a trait. A method that needs "copy if possible, else clone" has to be split in two, as `watch_reader.get` and `watch_reader.cloned` are.
15. `await yield` parses and checks but is not lowered on either backend.
16. A method that takes `self` and moves a non-`copy` part out of it leaves two owners. The standard library no longer has such methods: `unwrap` and `unwrap_or` were replaced by `x or else y`, which moves the payload out of the value it consumes. A user-written method that does `match self: @ok(v) => v` still leaves two owners: the caller keeps and later drops the original, and a temporary receiver is dropped right after the call. Chapter 14 forbids moving out of `self`, but the checker does not reject it inside a generic body over `T`. Fixing it needs a decision on how a method consumes its receiver.
17. Resolved 2026-11-14. A range index's `{len, data}` slice header is inline bytes in the caller's storage on both tiers ([value semantics](value-semantics.md)), so slicing allocates nothing. Corpus `202_value_loops_allocate_nothing` slices on each of 10000 passes under `# max-allocations: 2` and `# max-live-blocks: 0`.
18. Resolved 2026-11-14. Sums, tuples, `option[T]` results, and `generator.next()` results are inline bytes on both tiers ([value semantics](value-semantics.md)), and coroutine objects and `par`/`race` task tuples are freed. Corpus `202_value_loops_allocate_nothing` (ordinary functions and generators), `177_coroutine_borrow_storage`, `178_coroutine_objects_freed`, and `179_par_race_tasks_freed` require `# max-live-blocks: 0` with tight `# max-allocations:` bounds, on both tiers.
19. Chapter 16 says a closure that escapes captures by move, but no escape analysis exists. A closure without a capture list borrows each value it uses that is not `copy` (implemented 2026-11-13), so an escaping one that uses such a value is rejected where the borrow would outlive the value, with help that suggests `move`, instead of moving automatically. Implementing the rule needs an analysis that decides when a closure escapes (returned, stored in a longer-lived place, or sent to a task outside a `crew`).
20. In the storage form a task result that is not `copy` is moved out by the first `get()`, so a second `get()` on the same task reads a result that is no longer there. Chapter 28 says the `ok` results of a crew's tasks stay readable through `get()` after `c.errors()`. A `copy` result is read in place and can be read again; for any other result `c.errors()` is refused by name, because the list and the task would both own the error. Fixing it needs `get()` to give a borrow of the result the task keeps, or a rule that a non-`copy` result is read once.
21. A pattern binding reached through a `&mut` subject is treated inconsistently by the checker. Chapter 3 says such a binding names part of what the reference points at and "can be written". The checker accepts `xs.push(9)` on a plain `@some(xs)` binding of a `match` on a `&mut option[list[int32]]`, but rejects the assignment `n = n + 1` to a plain `@some(n)` binding of a `&mut option[int32]` and requires `@some(mut n)`. Either both should need `mut` or neither should. A write through such a binding reaches the referenced value (corpus 190).
22. A name bound inside an or-pattern alternative is refused by HIR lowering: `@a(n) | @b(n) => n` fails with "a name bound (directly, or via destructuring) inside one `|` alternative is not supported by this milestone", although the module type-checks. Chapter 13's or-patterns allow each alternative to bind the same names at the same types. Or-patterns without bindings lower, including on sums whose payloads need a drop.
23. Impls generated by an item-level splice (a `deriving` clause, or a user's `static def` returning a `def_expr`) are not ownership-checked: `check_ownership` walks only each file's own items, and a generated impl's spans point into the file that holds the quote, which the pass cannot name. A derived body that moves a non-`copy` field out of `self` (as `deriving ord` did through a by-value `ord_cmp` until it took references) is then caught only by the storage verifier, as an internal error rather than a diagnostic.
24. The bytes of a `str` built at run time are never freed, on either tier. Chapter 14 makes `str` `copy` ("an immutable view of shared bytes"), so no value owns the buffer that interpolation, `show`, or a `std.string` method allocates, and nothing drops it. `"{n}"` on an `int64` leaves two blocks (the digits and the joined result); a loop that formats a value on every pass grows without bound. Corpus 110 and 167 allow for these blocks. Fixing it needs an owner for run-time string bytes: an owned string type that `str` borrows from, an arena per scope, or reference counting.
25. A block `static for` is not unrolled when a loop variable holds a value with a part of a user sum type, such as `static for f in forms` over a `list[shape]`, or over a list of structs with a `shape` field. `materialize_static_value` gives no literal form for a variant, so the loop is left to lowering, which fails with "this `static for` was not unrolled during checking". Lists of numbers, strings, and structs of those unroll.
26. Compile-time code cannot read a non-scalar part of a struct-valued `static`: `static let b = area(h.form)` with `h` a struct static fails with "a struct-valued `static` has no runtime storage yet". The message is stale, because run-time code reads such statics since 2026-11-10. Reading the whole static (`area_of(h)`) works.
27. A run-time call of a `static def` inside a block `static for`, `total = total + score(it)`, is not evaluated at compile time even though every argument is known then; the program fails to compile with "`score` is not a function of this program". The same call in a `static if` condition runs.
28. Resolved 2026-11-14. `==` and `!=` on a tuple, an array, an `option`, or a `result` compare what they hold, through bounded `eq` impls in `std.traits` ([chapter 20](specification/02-intermediate/20-operator-overloading.md#equality-on-tuples-arrays-option-and-result)). `<` on them is an error, since the specification defines no order. Corpus `205_structural_equality` checks equal and unequal cases of each, nested ones, `str` and derived-struct elements, and the `T: eq` bound with `# expect:`; `check_test` covers the refusals.
29. A closure that takes ownership of a zero-sized value whose type has a drop (`type marker = {}` with `impl drop for marker`, captured by a `move` closure) is refused by name in the storage form: "a closure that takes ownership of a zero-sized value that needs a drop". A zero-sized capture takes no environment bytes, so an environment of only such captures is empty and has no drop glue to run the drop. Zero-sized captures without a drop compile (corpus `204_zero_sized_capture`). Fixing it needs the environment to keep drop glue even when it holds no bytes, and the capture to move the value out of a slot that has no storage.
30. A borrow of a callee's local can escape through a `&mut` parameter. `def fill(out: &mut list[&int32])` that does `let n: int32 = 5; out.push(&n)` is accepted, and the caller reads the dangling reference (`*out[0]` returned 5). The same happens when the local lives in an inner block of the function that owns the list. Chapter 14 says a borrow cannot outlive the value it borrows. Storing a value that carries a loan into a place reached through a parameter must require that loan to outlive the parameter's referent. Programs: `src/testdata/known_gaps/30_list_of_refs_escape.cn`, `30b_list_of_refs_escape_fn.cn`. The caller side has the same gap: `register(&mut r, src.as_slice())` with `register` pushing the view into `r.names` does not make `r` carry the loan, so `src.push(2)` is accepted while `r` is still read (`30c_store_success_mutate.cn`, `30d_store_on_success.cn`). A call must carry each loan its arguments may store into a place reached through a `&mut` argument into that argument's root.
31. The result of a `generator def` does not carry the borrows of its arguments. `var g = each(&xs)` followed by `xs.push(4)` while `g` is still used passes the ownership check; the same program with `std.iter.iter(&xs)` is rejected. The program then stops at code generation ("an iterator over a borrowed collection that is not a local"), which currently hides the hole. Program: `src/testdata/known_gaps/31_generator_borrow.cn`.
32. A value-indexed type with a `bool` parameter does not compare its index: `send(d, 1)` with `d: conn[false]` and `send` taking `conn[true]` is accepted and runs. A `usize` index is compared (`buf[4]` for `buf[8]` is a type mismatch). Program: `src/testdata/known_gaps/32_typestate_misuse.cn`. Cause, found 2026-11-15: the checker records both types as `conn[_]`; a `bool` index is left as an unknown slot, not interned as a value.
33. `replace(&mut xs[i], v)` on a `list[T]` fails with "conflicting types for `T`": `&mut xs[i]` produces `cell_mut[T]`, not `&mut T`. Chapter 14 recommends `replace` for exchanging an element. Program: `src/testdata/known_gaps/33_replace_elem.cn`.
34. When a call result keeps a closure's capture borrowed, the conflict diagnostic names the result binding as the closure: "cannot borrow `other` while the closure `r` is still in use", where the closure is `f` and `r` is `apply`'s result. Program: `src/testdata/known_gaps/34_callback_capture_origin.cn`.
35. A user sum type whose variants are named `@ok` and `@none` fails at HIR lowering: `match self: @ok(v) => v` in an `extend` method reports "no concrete checked type is available for this node" at `v`. The same type with variants named `@full` and `@empty` checks and lowers. The prelude's `ok` and `none` probably take the names in one resolution path and not the other. Building a value is refused too: `let s: shape = @ok(7)` reports "expected `shape`, found `result[_, _]`".
36. The block form of `on` bound to a name, `let w = on(cpu): ...`, checks and then fails at HIR lowering with "an `on(...)` did not resolve to a task type". `await on(cpu): ...` works.
37. A compound assignment to a list element, `xs[0] += 3` with `xs: list[int32]`, is refused on both tiers: "compound assignment through an `index_set` impl is not supported yet". `xs[0] = xs[0] + 3` works.
38. The checker treats `cell[T]` and `&T` as the same type, and `cell_mut[T]` and `&mut T`, in both directions, and accepts `*mut T` where `*T` is expected. `type_table::compatible` allows each pair and no conversion is recorded, so later stages see a value of one type where the other is declared. `list_iter.next` returns `@some(&self.src[i])`, a `cell[T]`, as an `option[&T]`, and `list.as_ptr` returns a `*mut T` as a `*T`. Found by the core verifier (rules E4 and S4); the adapter reports these functions as "implicit conversion" gaps. Item 33 is the same confusion seen from user code.
39. A `for x in xs` over a borrowed collection (`xs: &list[int32]`) calls the consuming `into_iter` on a bitwise copy of the collection. The checker allows it only when the elements are `copy` and rejects it otherwise ("would give the value two owners"), and it runs correctly on both tiers. It is a special case with no general rule behind it: the call moves a value out of a reference, which the core's rules forbid. The core spells it with the `bitwise_copy` intrinsic, which exists only for this loop. The loop should call the borrowing `iter` and copy each element, as `for x in &xs` with `*x` does, and `bitwise_copy` should then be removed.
40. A type invariant is not checked after a field write made through a reference. `self.value = v` in a `mut self` method and `p.value = v` with `p: &mut pos` both leave `value > 0` broken with no panic, on both tiers; the same write on a local `var` panics with "invariant violated". Chapter 34 says an invariant is checked wherever a field is written. HIR lowering looks the invariant up on the type of the object expression, which is `&mut pos` here and has none. Programs: `src/testdata/known_gaps/40_invariant_write_in_mut_self_method.cn`, `40b_invariant_write_through_mut_ref.cn`.
41. The checker records an unsettled type for a struct literal whose field is initialized with `@none`. In `def mk[I, T](it: I) -> wrap[I, T]: return wrap { inner: it, last: @none }` with `type wrap[I, T] = { inner: I, last: option[T] }`, the literal's recorded type is `wrap[I, _]` in the template and `wrap[int32, _]` in the instance `mk$int32$int64`, although the return type fixes `T`. The program compiles and runs, because lowering takes the type from elsewhere. The typed core cannot hold an unsettled type, so the adapter leaves these functions out: ten `std.algo` iterator adapters (`chain`, `enumerate`, `flat_map`, `flatten`, `peekable`, `rev`, `skip`, `step_by`, `take`, `zip`). An `@none` passed to a generic parameter, `pick(@none, 4)`, is recorded as `option[_]` the same way.

42. In a task, a suspension in a position that cannot go ahead of its statement is refused at lowering: an `await` (also `await par`/`race`/`on`), a `?`, a `crew` or `crew.errors()` on the right side of `and`/`or`, in an `elif` condition, or in a match guard. The messages are "an `await` that is evaluated conditionally or repeatedly (...) is not lowered yet; await into a `let` first" and "a `?` in a task, or leaving a `crew` block, from a place where a task cannot suspend (...) is not lowered yet; move it into a statement". The entry `async def main` is exempt (it blocks the thread), as are a plain loop condition and a value-producing `if`/`match` branch. Chapter 27 documents the `and`/`or` and `elif` rejection but the checker accepts the program and the error comes from code generation. Programs: `src/testdata/known_gaps/42_conditional_suspension_in_task.cn`, `42b_await_on_right_of_or.cn`, `42c_try_on_right_of_and.cn`.
43. A `def` or `use` inside a function body type-checks and is then refused at lowering ("statement kind 12 is not lowered yet" and "statement kind 3 is not lowered yet"). A `type` inside a function body is not declared: `pt { x: 4 }` reports "undefined type `pt`". An `impl` in a function body is a parse error ("expected a statement but found `impl`"). The specification does not say whether declarations may appear in a function body. Programs: `src/testdata/known_gaps/43_nested_def_in_function.cn`, `43b_nested_use_in_function.cn`, `43c_nested_type_in_function.cn`.
44. A `static let` inside a function body is not supported. If the name is never read, lowering refuses it ("this `static` declaration is not lowered as a function-body statement"). If it is read, the checker reports "undefined name `k`". The specification covers `static if` and `static for` in function bodies but not a local `static let`. Programs: `src/testdata/known_gaps/44_local_static_let.cn`, `44b_local_static_let_read.cn`.
45. An open-ended range is accepted by the checker and refused at lowering: `for i in 3..:` reports "range is missing a bound" and `let r = 3..` reports "binary expression is missing an operand". Programs: `src/testdata/known_gaps/45_open_range_in_for.cn`, `45b_open_range_value.cn`.
46. A bare `yield` in a generator, `generator def ticks() -> some iterator[unit]: yield`, is refused at lowering with "`yield` with no value is not supported". Program: `src/testdata/known_gaps/46_bare_yield.cn`.
47. 48. 49. 50. 51. 52. `?` applied to a reference to an `option` or `result`, `o?` with `o: &option[int32]`, type-checks and is refused at lowering: "`?` operand did not resolve to a concrete result/option type". 54. 57. On the typed-core path, a generic instance that calls a trait default copied for a generic impl cannot be built. `map_iter::size_hint` on a `map_iter[filter_iter[...]]` calls `filter_iter`'s copy of the `iterator` default `size_hint`, whose signature still names the impl's parameters (`&filter_iter[I, T]`); the core has no form for a call that substitutes them, and the old lowerer lowers that copy once with the parameters left abstract. Six `std_test` programs fail in only mode: `iter_adapters` and `iter_adapters_nesting` because of this, and `iter_adapters_compose`, `iter_adapters_pairing`, `iter_adapters_slicing` and `zip_open_literal_argument` because of todo 41. 58. On the typed-core path, an `|` pattern below the top of a pattern, `(1 | 3, y) => y`, is not built: the adapter leaves the function out ("nested or pattern"). The old lowerer compiles it. Only mode refuses such a program as a compiler gap.
