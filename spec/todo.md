5. `zero`/`one`/`hash` have no impls for the 128-bit types (`int128`, `uint128`, `float128`), because a reachable module is compiled in full and the bytecode VM has no representation for them yet — an `impl zero for int128` in `std.traits` makes every program fail to compile. They arrive with codegen increment 6, alongside the rest of 128-bit support.
6. **Scope-exit `drop` glue: done for the common case, with real gaps left.** `checker::resolve_drop_plans` (`src/semantic/check.cpp`) resolves, for every struct/sum type, its own `impl drop` (if any) plus every struct field that is itself droppable, into `checked_types::drop_plans`. `hir::compute_drop_schedule` (`src/hir/drop_schedule.{h,cpp}`) walks each function/lambda body (mirroring `move_check.cpp`'s move-tracking rules, but with an inverted, safety-first branch-merge policy — see that file's class doc comment) to schedule reverse-declaration-order drop calls at normal scope exit and at `return`/`break`/`continue`; `hir::lowerer` (`src/hir/lower.cpp`) synthesizes the actual `hir_call`s, needing zero new backend code on either tier (a scope-exit drop is an ordinary compiled function call). Verified end-to-end, both backends, exact printed output: `src/testdata/std_test/scope_exit_drop.kira` — reverse order, a moved-from binding never dropping, implicit field-wise drop for a struct with no own `impl drop`, and drop firing correctly on early `return`/`break`/`continue`. Direct `x.drop()` is rejected (`src/testdata/semantic_check_test/reject_direct_drop_call.kira`).

   Remaining gaps, each left deliberately rather than silently:
   - **A block/function whose tail is a real (non-`unit`) value skips scope-exit drop for that scope entirely**, rather than dropping after materializing the tail into a temporary. Both `bytecode_compiler` and `llvm_codegen` read a value-typed block's tail structurally off its last statement, so a drop call appended there would silently become the new (wrong) tail value; the conservative fix is to not schedule the drop at all — a leak, never a double-drop or use-after-drop, on the branch that hits it. Needs a real temporary-materialization pass to close.
   - **A value-returning `return expr` never gets scope-exit drops for locals `expr` merely borrows from** (e.g. `return h.get_id()`) — `hir_return`'s value is evaluated as part of compiling the return itself, so a drop inserted ahead of the whole statement would run before that read. (A local `return`s *directly*, like `return h`, is unaffected: it's recorded as moved and excluded from the schedule.) Bare `return`/`break`/`continue` are unaffected.
   - **Match-arm, `for`-loop, and destructuring `let`/`var`/parameter pattern bindings are not tracked at all** — only a plain `let name = expr`/`var name = expr`/simple parameter is. A droppable value bound this way (`@some(h) => ...`, `for h in handles`) is never scheduled for a drop; today's `into_iterator`/`for` desugaring in particular routes a loop variable through exactly this untracked path.
   - **Sum-type field-wise drop is not implemented** — only a sum type's own `impl drop` runs; recursing into a matched variant's payload needs a synthesized tag-dispatch this pass doesn't build. `vector[T]`'s eventual `impl drop` (a struct) doesn't need this.
   - **Unwinding through drops on panic** is moot as stated: this compiler has no stack unwinding at all (`panic`/`assert` compile to an unconditional trap/abort, not a raiseable condition).
   - **The prelude `drop(x)` free function still does not exist.** `def drop` is declared only as the trait method; a call to bare `drop(x)` is still accepted by the checker and then fails in lowering with "no concrete checked type is available for this node" — a confidently wrong diagnostic for what is really an unresolved name.

   `src/semantic/move_check.h:13`'s description of move checking as the analysis destructors need underneath them remains accurate; `hir::compute_drop_schedule` is a second, HIR-oriented walker built alongside it (not a replacement) — see that file's doc comment for why. `spec/list-migration-design.md`'s "Phase 0" narrowed what phase 4 (flipping `list[T]`) actually needs from this item to reverse-order drop, moved-from exclusion, and struct field-wise drop — all three now hold for the common (plain-`let`, non-value-tail) case phase 4 will exercise.
7. **`shared[T]` is a name with nothing behind it.** `shared` is registered as a builtin generic (`src/semantic/types.cpp:51`) and that is the whole implementation: `let a: shared t = shared t{ id: 1 }` fails with ``expected `shared[t]`, found `&t` `` — the `shared` expression form produces a plain reference — and `shared[T]` has no methods at all, so `.clone()` does not resolve. No atomic reference count exists anywhere. Paired with item 6 (the refcount-reaching-zero drop), this is the other half of [17-shared-ownership-and-drop.md](specification/02-intermediate/17-shared-ownership-and-drop.md).
8. **`scope:` blocks do not parse.** `scope_stmt = "scope" ":" block` is in [kira-grammar.ebnf](kira-grammar.ebnf) line 524 and is referenced normatively by the drop chapter as *the* way to end a binding's lifetime early, but there is no `kw_scope` token and no parser support — `scope:` reports "expected end of line after this". Related to item 2 but distinct: this is the bare lexical scope already in the grammar, not a `with`-style context manager.
9. **`just run` silently loses the standard library.** `bazelisk run //src:kira -- file.kira` runs with the runfiles tree as its working directory, where `find_stdlib_source_file` (`src/driver/driver.cpp:185`) finds none of its candidates. The stdlib is then never injected, so `println` type-checks but fails to lower, and the driver reports ``no concrete checked type is available for this node ... this is a gap in the compiler, not a mistake in your code`` — a confidently wrong diagnostic for correct code, pointing the user at the compiler rather than at their invocation. `./bazel-bin/src/kira file.kira` from the repo root works fine. Either make the runfiles candidate resolve under `bazel run`, or have the driver diagnose a missing stdlib explicitly instead of letting it surface as a bogus lowering gap.

10. **A user module named `s` collides with `std.test`'s internals.** Compiling a file declaring `module s` emits five spurious errors of the form ``module-qualified reference `s.before_all` does not resolve from module `std.test` `` (also `s.cases`, `s.before_each`, `s.after_each`, `s.after_all`). `std.test` evidently uses `s` as a module-qualified binder that resolves against the global module namespace, so any user module of that name shadows it. Renaming the user module to `s2` makes the errors vanish.

12. **A module-qualified generic call cannot be monomorphized.** `mem.alloc[int32](4)` — a qualified path with explicit generic arguments — fails with "cannot compile `alloc` for this call: its body uses a construct generic instantiation doesn't support yet ... cannot clone this construct for monomorphization: a method call with generic arguments". The unqualified form (`use std.mem.alloc` then `alloc[int32](4)`) works. `ast_clone` does not handle the qualified-call-with-bracket-arguments shape, so the workaround is to import the name; the two spellings should not differ.

15. **`uninit[T, N]`'s stack storage is capped at 64 KiB per frame** and is not checked against the platform's real stack limit. `op_stack_alloc` encodes its offset as a 16-bit immediate, so a function whose buffers exceed that is refused with an explicit diagnostic rather than miscompiled — but a function *under* that limit can still overflow a small thread stack with no warning, and the LLVM tier (which uses `alloca` and has no such cap) will accept frames the bytecode tier rejects. The two tiers should agree, and the limit should be a real one rather than an encoding artifact.

16. **`list[T]` is a library type now; the sweep behind it is unfinished.** `list[T]` is an ordinary generic struct in `src/std/list.kira`, written in Kira over `std.mem` and the `machine` layer, reaching the language through `std.traits`'s `index`/`index_mut`/`index_set`/`from_array` and `std.iter`'s `into_iterator` — the same four traits any user collection can implement. It is gone from `k_builtin_generic_arities` and from `k_builtin_methods`, and `range[T]` followed it out (an ordinary struct in `std.traits`, needed so `impl index[range[usize]]` can receive a range and read its bounds). What remains of [list-migration-design.md](list-migration-design.md)'s phase 4 is cleanup and consequences, tracked as items 17-20 below, plus two pieces of now-dead compiler code: `is_list_type`/`resolve_container_view`'s `list` arm in **both** backends (`src/bytecode_compiler/compile.cpp:1025`, `src/llvm_codegen/codegen.cpp:980` — each tests `builtin_generic_kind`, which `list` no longer is, so the arms can never fire), and `list_reserve_slot` in the runtime with its LLVM declaration (`src/llvm_codegen/codegen.h:86`). The benchmark that phase 4 said to take *before* flipping — sort 100k `int32`, both tiers, both allocator modes — was never taken; every `list` index is a real call now, and there is no number saying what that cost.

17. **A read-borrow of an element, `&v[i]`, has no route on a user collection.** `v[i]` on a type implementing `index` is a call to `at`, which answers a *value*; `&` of that value has no place to point at, so lowering refuses it with "cannot take the address of this expression — `&`/`&mut` needs a place that exists in memory" (`src/bytecode_compiler/compile.cpp:2424`, `src/llvm_codegen/codegen.cpp:2536`). The checker accepts it and types it `&T`, so this surfaces as a codegen failure on correct-looking code rather than as a diagnostic at the borrow. `&mut v[i]` works — that is exactly what `index_mut`'s `at_mut` exists for — and the asymmetry is the tell: the read half needs its own trait (an `index_ref`, answering `cell[self.output]`) the way the write half already has one. `std.iter`'s borrowing iterators depend on it (`src/std/iter.kira:142`, `let slot = &self.src[self.at]`), which blocks `src/testdata/std_test/iter_adapters_{compose,nesting,pairing,slicing}.kira` and `compound_where_bound.kira`.

18. ~~A `list[T]` parameter in `std.io` degrades to the bare constructor `list`, depending on which module is the compile entry point.~~ *(Fixed.)* The actual defect was not in name resolution at all — `resolve_named_type` and `find_builtin_impl_method` were innocent. `checker::build_method_table` (`src/semantic/check.cpp`) set its one-shot `methods_built_` guard *before* finishing its work, then called `monomorphize_trait_default` inline as each impl was visited; that call type-checks a clone of a trait-default body (e.g. `std.io`'s `reader::read_to_end`, whose default body calls `out.push(...)` on a `list[byte]`), which can itself call back into `find_method`/`build_method_table` reentrantly. Because the guard was already set, the reentrant call saw whatever subset of `methods_`/`extend_methods_by_builtin_` the outer loop had populated *so far* — order-dependent on `index_.modules`'s unordered iteration order, i.e. on which module happened to be the compile's entry point (entry files keep their original position when `inject_stdlib_prelude` skips re-adding an already-present source). Fixed by splitting `build_method_table` into two passes: register every `extend`/impl method for every module first (no `check_function` calls, so no reentrancy risk), then monomorphize every deferred trait default only once that is complete, so a reentrant lookup always sees the fully built table.

    Fixing this surfaced a second, distinct, pre-existing bug: `//src:cli_test`'s `test_run_index_mut_dispatches_to_cell_mut` (previously masked because the process aborted at item 18's assertion before reaching it) is itself stale — it still declared `index_mut`'s old `type output = int32` shape rather than the `type output_mut = cell_mut[int32]` item 19 (now removed from this file, "index_mut ... implemented end to end") introduced — and, once that's corrected, fails a different way that reproduces only when run after enough other tests in the same process (a lone repro via `./bazel-bin/src/kira` on the identical source succeeds, and a handful of preceding tests together with it also pass). Something order- or allocation-history-dependent, not yet isolated to a specific prior test, causes `checker::require_index_mut_trait`'s `index_mut_dispatches_` entry to go unseen by `hir::lower_unary`'s `&mut v[i]` special case, falling through to the ordinary `addr_of` path and failing bytecode compilation with "cannot take the address of this expression". Needs isolating what state actually leaks across `compile_sources` calls within one process — a session/type-table object that outlives a single call would explain it, but none has been found yet.
