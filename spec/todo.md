5. `zero`/`one`/`hash` have no impls for the 128-bit types (`int128`, `uint128`, `float128`), because a reachable module is compiled in full and the bytecode VM has no representation for them yet — an `impl zero for int128` in `std.traits` makes every program fail to compile. They arrive with codegen increment 6, alongside the rest of 128-bit support.
6. **`drop` destructors never run.** The `drop` trait exists (`std.traits`), an `impl drop for T` type-checks, and the method compiles and is callable — but nothing in the compiler ever *invokes* it. There is no scope-exit glue on either backend: `"drop"` appears nowhere in `src/**/*.{cpp,h}` as a recognized trait name, and there is no `emit_drop`/`drop_glue`/`destructor` code path. Verified end-to-end: a `noisy` type whose `drop` prints produces no output when its owner's scope ends, identically on the bytecode VM and the LLVM AOT tier, while an explicit `b.drop()` prints as expected. Real consequence today: `impl drop for file_handle` (`src/std/io.kira:159`) means every `file_handle` not explicitly `.close()`d leaks its fd, silently. `src/semantic/move_check.h:13` describes move checking as the analysis destructors "need underneath them" — that substrate is built; the glue that stands on it is not. This blocks any real heap allocator (a `free` primitive is worse than useless without destructors) and therefore blocks rebuilding `list[T]` in the standard library. Sub-items, all unimplemented: reverse-declaration-order drop within a scope; implicit field-wise drop for aggregates; not dropping a moved-from binding; unwinding through drops on panic; the prelude `drop(x)` free function (no `def drop` exists outside the trait declaration and `std.io`'s impl — a call to `drop(x)` is nevertheless accepted by the checker and then fails in lowering with "no concrete checked type is available for this node", a confidently wrong diagnostic for what is really an unresolved name); and rejecting the direct `x.drop()` call that [17-shared-ownership-and-drop.md](specification/02-intermediate/17-shared-ownership-and-drop.md) says must not be callable but which the checker currently accepts.
7. **`shared[T]` is a name with nothing behind it.** `shared` is registered as a builtin generic (`src/semantic/types.cpp:51`) and that is the whole implementation: `let a: shared t = shared t{ id: 1 }` fails with ``expected `shared[t]`, found `&t` `` — the `shared` expression form produces a plain reference — and `shared[T]` has no methods at all, so `.clone()` does not resolve. No atomic reference count exists anywhere. Paired with item 6 (the refcount-reaching-zero drop), this is the other half of [17-shared-ownership-and-drop.md](specification/02-intermediate/17-shared-ownership-and-drop.md).
8. **`scope:` blocks do not parse.** `scope_stmt = "scope" ":" block` is in [kira-grammar.ebnf](kira-grammar.ebnf) line 524 and is referenced normatively by the drop chapter as *the* way to end a binding's lifetime early, but there is no `kw_scope` token and no parser support — `scope:` reports "expected end of line after this". Related to item 2 but distinct: this is the bare lexical scope already in the grammar, not a `with`-style context manager.
9. **`just run` silently loses the standard library.** `bazelisk run //src:kira -- file.kira` runs with the runfiles tree as its working directory, where `find_stdlib_source_file` (`src/driver/driver.cpp:185`) finds none of its candidates. The stdlib is then never injected, so `println` type-checks but fails to lower, and the driver reports ``no concrete checked type is available for this node ... this is a gap in the compiler, not a mistake in your code`` — a confidently wrong diagnostic for correct code, pointing the user at the compiler rather than at their invocation. `./bazel-bin/src/kira file.kira` from the repo root works fine. Either make the runfiles candidate resolve under `bazel run`, or have the driver diagnose a missing stdlib explicitly instead of letting it surface as a bogus lowering gap.
10. **A user module named `s` collides with `std.test`'s internals.** Compiling a file declaring `module s` emits five spurious errors of the form ``module-qualified reference `s.before_all` does not resolve from module `std.test` `` (also `s.cases`, `s.before_each`, `s.after_each`, `s.after_all`). `std.test` evidently uses `s` as a module-qualified binder that resolves against the global module namespace, so any user module of that name shadows it. Renaming the user module to `s2` makes the errors vanish.
