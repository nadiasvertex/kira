1. Unicode locale-tailored casing (Turkish/Azeri, Lithuanian — needs a locale parameter threaded through every casing call), NFC/NFD normalization, and grapheme-cluster segmentation (UAX #29) so `reversed`/`split` operate on graphemes rather than scalars.
2. "with" style scoped blocks.
3. Store and load binary AST instead of reparsing.
4. Store and load generated bytecode instead of recompiling.
5. `float128` has no representation on either backend, so it has no `zero`/`one`/`hash`/scalar trait impls and no `std.limits` answers. A reachable module is compiled in full, so an impl naming it would break every program. It needs a soft-float implementation: LLVM's `fp128` lowers to compiler-rt/libgcc calls, and Apple arm64 has no `fp128` support at all, so the runtime has to supply the arithmetic itself.
6. `std.limits.min[int64]()` (and `min[int128]()`, `min[int32]()`, ...) fails at compile time with "an integer overflowed its type". The body `-9223372036854775808 as T` is evaluated as `-(9223372036854775808 as T)`, so the cast overflows before the negation. The diagnostic's primary label also points at the wrong file: it shows a line of `limits.cn` with the caller's span.
7. A call to a `static pure def` from `std.limits` in ordinary run-time code fails at code generation: `let a = min[int64]()` in `main` reports "call to `min$int64` could not be resolved to a function in this compiled module". Binding it to a `static let` first works.
8. A module-qualified call with explicit type arguments does not bind them: `use std.limits` then `limits.max[int32]()` reports "cannot tell what `T` is in this call to `max`". `use std.limits.max` then `max[int32]()` works.
9. A trait's static method called directly on a builtin type fails at code generation: `int64.zero()` (with `use std.traits.zero`) reports "no concrete checked type is available for this node". The same call through a bound (`T.zero()` with `T: zero`) works.
10. On Linux x86-64, `int128` checked multiplication may lower to a call to `__muloti4`, which libgcc does not provide. Untested; macOS links it from compiler-rt.
11. A compound assignment through a dereference, `*p += x` with `p: &mut int32`, is not supported on either backend. `*p = *p + x` works. This also blocks the next item.
12. There is no mutable deref trait, so `*guard += 1` on a `mutex_guard` (chapter 30's example) cannot compile. `std.sync` guards offer `get_mut()` and `set(value)` instead.
13. A bare `on(ctx, t)` or `on(ctx): body` value that is dropped without being awaited leaks what its inner task captured: the wrapper's drop does not drop the inner task's captures.
14. `implements[T, copy]` cannot be used, because `copy` is a concept rather than a trait. A method that needs "copy if possible, else clone" has to be split in two, as `watch_reader.get` and `watch_reader.cloned` are.
15. `await yield` parses and checks but is not lowered on either backend.
16. A method that takes `self` and moves a non-`copy` part out of it leaves two owners. The standard library no longer has such methods: `unwrap` and `unwrap_or` were replaced by `x or else y`, which moves the payload out of the value it consumes. A user-written method that does `match self: @ok(v) => v` still leaves two owners: the caller keeps and later drops the original, and a temporary receiver is dropped right after the call. Chapter 14 forbids moving out of `self`, but the checker does not reject it inside a generic body over `T`. Fixing it needs a decision on how a method consumes its receiver.
17. A range index `xs[a..b]` allocates its `{len, data}` slice header on the heap on both tiers, and nothing frees it, in any function. A loop that slices on every pass grows without bound; `std.io`'s `read_to_end` and `read_exact` do this.
18. Sum-type and tuple values are heap blocks that nothing frees, on both tiers. Each `option[T]` a call returns, each tuple, and each `generator.next()` result leaks one block, so a loop that builds one per pass grows without bound. `par` and `race` also leak the tuples lowering builds for their tasks and results (corpus `179` allows for these).
19. Chapter 16 says a closure that escapes captures by move, but no escape analysis exists. A closure without a capture list borrows each value it uses that is not `copy` (implemented 2026-11-13), so an escaping one that uses such a value is rejected where the borrow would outlive the value, with help that suggests `move`, instead of moving automatically. Implementing the rule needs an analysis that decides when a closure escapes (returned, stored in a longer-lived place, or sent to a task outside a `crew`).
20. In the storage form a task result that is not `copy` is moved out by the first `get()`, so a second `get()` on the same task reads a result that is no longer there. Chapter 28 says the `ok` results of a crew's tasks stay readable through `get()` after `c.errors()`. A `copy` result is read in place and can be read again; for any other result `c.errors()` is refused by name, because the list and the task would both own the error. Fixing it needs `get()` to give a borrow of the result the task keeps, or a rule that a non-`copy` result is read once.
21. A pattern binding reached through a `&mut` subject is treated inconsistently by the checker. Chapter 3 says such a binding names part of what the reference points at and "can be written". The checker accepts `xs.push(9)` on a plain `@some(xs)` binding of a `match` on a `&mut option[list[int32]]`, but rejects the assignment `n = n + 1` to a plain `@some(n)` binding of a `&mut option[int32]` and requires `@some(mut n)`. Either both should need `mut` or neither should. Separately, the pointer form copies such a binding, so a write through it does not reach the referenced value there; the storage form writes in place (corpus 190 records both answers).
22. A name bound inside an or-pattern alternative is refused by HIR lowering on both forms: `@a(n) | @b(n) => n` fails with "a name bound (directly, or via destructuring) inside one `|` alternative is not supported by this milestone", although the module type-checks. Chapter 13's or-patterns allow each alternative to bind the same names at the same types. Or-patterns without bindings lower on both forms, including on sums whose payloads need a drop.
23. Impls generated by an item-level splice (a `deriving` clause, or a user's `static def` returning a `def_expr`) are not ownership-checked: `check_ownership` walks only each file's own items, and a generated impl's spans point into the file that holds the quote, which the pass cannot name. A derived body that moves a non-`copy` field out of `self` (as `deriving ord` did through a by-value `ord_cmp` until it took references) is then caught only by the storage verifier, as an internal error rather than a diagnostic.
