7. A struct literal whose head carries explicit type arguments does not parse. `box[int32] { cur: @none }` reports "expected end of line after this" pointing at the `]`, so an explicitly-instantiated generic struct can only be built where inference supplies the arguments (a `return` into a declared type, an annotated `let`). The module-qualified head `q.holder { ... }` was the same shape of gap and is now fixed; this is the remaining one — `parse_postfix` does not consider a `{` after a bracketed type-argument list. Found while testing the generic-impl method fix.
8. ~~A self-qualified module path does not resolve.~~ Done. A submodule declared inline in the same file is now first-class: `main.inner.holder` and the relative `inner.holder` both resolve in type position, as a struct-literal head, and in call position, `super.a.holder` reaches a sibling submodule, and a submodule's `def`s (including generic ones, whose monomorphized instances are owned by the submodule's own dotted name) are lowered into a module of their own so calls into them run on both tiers. Module-qualified `static` reads (`main.inner.limit`, and the cross-file `r.limit` after `use p.r`, which had the same gap) lower to their evaluated constant. Two related bugs found and fixed on the way: a same-line module body (`module inner: pub type holder = ...`) was silently dropped by the parser and its items were parsed as the *parent* module's, and compile-time `static` values were memoized by bare name in one flat namespace, so a parent and a submodule that each declared `static limit` both read whichever was evaluated first.
9. The multi-line sum-type form does not parse. `spec/kira-reference.md` documents it in three places (lines 445, 512, 594) as a `=` followed by indented `| @variant` lines, and it reports "expected end of type block (dedent)" pointing at the first `|`. Only the single-line form (`type direction = @north | @south`) works, which is what every declaration in `src/std` uses — so the gap has stayed invisible. Either the parser accepts the documented form or the reference stops documenting it; the former, since the multi-line form is the readable one for a sum type with payloads.
10. `deriving ord` type-checks but `cmp` does not lower: `a.cmp(b)` on a `deriving ord` type fails with "no concrete checked type is available for this node". `ord` is deliberately excluded from `k_real_derive_traits` (`src/semantic/check.cpp`) and stays on the type-check-only `derived_method_result` path. Its return type `ordering` is now a real sum type, so the remaining work is a real derived `cmp` — a lexicographic field-by-field comparison — which also needs `ord` impls for the primitive field types.
11. A compound bound in a `where` clause cannot be cloned for monomorphization. `def sum[I, T](it: I) -> T where I: iterator[T], T: add + zero` reports "cannot clone this construct for monomorphization: this type-expression shape" pointing at `add + zero`; splitting it to a single bound compiles. `std.algo`'s `sum` and `product` are written `T: zero` and `T: one` for this reason rather than the `T: add + zero` / `T: mul + one` design §6.1 specifies.
12. A lambda capturing a mutable local collection does not lower. `var seen: list[int32] = []` followed by `xs.into_iter().for_each((x) => seen.push(x * 2))` type-checks and then fails with "no concrete checked type is available for this node" pointing at `seen.push`. Found while testing `for_each`, whose only observable effect is a capture.
13. `zero`/`one` have no impls for the 128-bit types (`int128`, `uint128`, `float128`), because a reachable module is compiled in full and the bytecode VM has no representation for them yet — an `impl zero for int128` in `std.traits` makes every program fail to compile. They arrive with codegen increment 6, alongside the rest of 128-bit support.
