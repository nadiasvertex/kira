1. Full Unicode case mapping and folding for `std.string` are done (`std.unicode`/`std.unicode_tables`, pure Kira over generated UCD tables — see [52-std-string.md](specification/04-stdlib/strings-and-formatting/52-std-string.md)). Still deferred, each needing more work than "read another generated table": locale-tailored casing (Turkish/Azeri dotted/dotless-I, Lithuanian dot-retention — needs a locale parameter threaded through every casing call), NFC/NFD normalization, and grapheme-cluster segmentation (UAX #29) so `reversed`/`split` can operate on graphemes rather than scalars.
2. "with" style scoped blocks.
3. store and load binary AST instead of reparsing
4. store and load generated bytecode instead of recompiling
5. A derivation that dispatches on a field's *concrete* type. `f.type_name` (`render_type_expr`, `src/comptime/reflect.cpp`) is still syntactic — generic arguments collapse to `"[..]"`, every non-`named_type` shape renders `"<type>"`, aliases are unresolved, and inside a generic declaration a `T` field reports `"T"` rather than the instantiation's type, because `comptime::value`'s type value carries no bindings. None of the five derivations reads `type_name`, so nothing is blocked; the working mechanism for type-dependent behaviour today is `T.name()` in ordinary generic code (`type_param_reflection`), which is how `std.algo`'s `sort[T]` selects a radix sort.
6. `zero`/`one`/`hash` have no impls for the 128-bit types (`int128`, `uint128`, `float128`), because a reachable module is compiled in full and the bytecode VM has no representation for them yet — an `impl zero for int128` in `std.traits` makes every program fail to compile. They arrive with codegen increment 6, alongside the rest of 128-bit support.
7. `deriving hash`  does not lower through the HIR/LLVM tier at all yet — `a.hash()` on any `deriving hash` type fails HIR lowering with "no concrete checked type is available for this node" — so this fix, like the rest of `deriving hash`, is exercised only via the tier-0 bytecode VM (`cli_test.cpp`'s `run` mode), not `codegen_stress_test`.
9. `static if`'s branch bodies now accept ordinary statements (`return`, `let`, an assignment, ...), not just declarations — `parser::parse_static_branch_node` dispatches each line to whichever parses, and inside a generic `static def[T]` a `T`-dependent condition (e.g. `T.name() == "int64"`) is deferred (both branches type-checked, real selection per call once `T` is bound) rather than erroring during template checking. This still doesn't help the underlying problem for an *ordinary* (non-`static`) generic function: every branch of an ordinary `if`-chain there still type-checks against the same concrete `T`, so `if n == "int64": return SOME_INT64_LITERAL as T` still fails for `T = int32` even though that branch is dead for `int32` — the literal must fit *every* `T` the function is ever instantiated at, and `static if` is only usable inside a `static def` (a comptime-interpreted function), not a regularly-compiled one, since nothing lowers a `static_decl` to HIR. `std.limits.min`/`max` (both `static def`) still use the fixed-width-local workaround (`var v: int64`/`var v: uint64` accumulated across every branch, cast to `T` only once in the final `return`) rather than `static if`, because the comptime evaluator has no `cast_expr` (`as`) support yet — a real, separate gap surfaced while fixing this one.
10. The most-negative integer literal for a width can't be written directly — `-9223372036854775808` (`int64::MIN`) is rejected as "too large for `int64`", because the literal's positive magnitude is validated before unary `-` is applied, and `9223372036854775808` is one past `int64::MAX`. Write `-9223372036854775807 - 1` instead (the same trick works at any width).
11. Formatting exactly `int64::MIN` via string interpolation panics with "integer overflow" at runtime, even though arithmetic/comparison against that exact value works fine — looks like a classic `abs(INT64_MIN)` overflow in the int-to-string formatting path (`src/runtime/fmt.*` or the bytecode VM's equivalent).
12. The compile-time evaluator (`src/comptime/eval.cpp`) has no `ast::node_kind::cast_expr` case at all — any `<expr> as <type>` reached during compile-time evaluation (a `static def`'s body, a `static let` initializer, a `static if`/`static assert` condition) fails with "this expression form is not yet supported in compile-time evaluation", regardless of whether the cast itself is a legal, statically-known conversion. This is why `std.limits.min`/`max` (both `static def[T]`) build their result in a fixed-width local across every branch and cast to `T` only once, in the final `return`, rather than `return <value> as T` per branch. No caller in the tree currently exercises a generic `static def[T]` from ordinary (non-comptime) code either — `min[T]()`/`max[T]()`/`bits[T]()`/`digits[T]()` have zero call sites outside `src/std/limits.kira` itself — so calling one from a plain function currently fails separately, with `error: call to '<name>$<T>' could not be resolved to a function in this compiled module` at bytecode-compile time (the ordinary-call fold path silently falls through to treating the never-lowered `static def` instance as an emittable callee instead of erroring or retrying); this surfaced while regression-testing item 9's `static if` fix and needs its own investigation.
