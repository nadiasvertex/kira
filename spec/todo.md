2. "with" style scoped blocks.
3. store and load binary AST instead of reparsing
4. store and load generated bytecode instead of recompiling
5. `zero`/`one`/`hash` have no impls for the 128-bit types (`int128`, `uint128`, `float128`), because a reachable module is compiled in full and the bytecode VM has no representation for them yet — an `impl zero for int128` in `std.traits` makes every program fail to compile. They arrive with codegen increment 6, alongside the rest of 128-bit support.
6. **`drop` destructors never run.** The `drop` trait exists (`std.traits`), an `impl drop for T` type-checks, and the method compiles and is callable — but nothing in the compiler ever *invokes* it. There is no scope-exit glue on either backend: `"drop"` appears nowhere in `src/**/*.{cpp,h}` as a recognized trait name, and there is no `emit_drop`/`drop_glue`/`destructor` code path. Verified end-to-end: a `noisy` type whose `drop` prints produces no output when its owner's scope ends, identically on the bytecode VM and the LLVM AOT tier, while an explicit `b.drop()` prints as expected. Real consequence today: `impl drop for file_handle` (`src/std/io.kira:159`) means every `file_handle` not explicitly `.close()`d leaks its fd, silently. `src/semantic/move_check.h:13` describes move checking as the analysis destructors "need underneath them" — that substrate is built; the glue that stands on it is not. *Update:* a real allocator and a standard-library list landed anyway (`std.mem`, `std.list`'s `vector[T]`), with `free` explicit rather than automatic — so this no longer *blocks* that work, it makes the result leak. A `vector` that goes out of scope without `free` leaks its buffer under `KIRA_ALLOCATOR=system`; under the bump arena it leaks exactly as everything already did. Scope-exit drop remains the thing that would make `vector[T]` safe to use without remembering, and is the prerequisite for `list[T]` itself moving onto that storage. Sub-items, all unimplemented: reverse-declaration-order drop within a scope; implicit field-wise drop for aggregates; not dropping a moved-from binding; unwinding through drops on panic; the prelude `drop(x)` free function (no `def drop` exists outside the trait declaration and `std.io`'s impl — a call to `drop(x)` is nevertheless accepted by the checker and then fails in lowering with "no concrete checked type is available for this node", a confidently wrong diagnostic for what is really an unresolved name); and rejecting the direct `x.drop()` call that [17-shared-ownership-and-drop.md](specification/02-intermediate/17-shared-ownership-and-drop.md) says must not be callable but which the checker currently accepts.
7. **`shared[T]` is a name with nothing behind it.** `shared` is registered as a builtin generic (`src/semantic/types.cpp:51`) and that is the whole implementation: `let a: shared t = shared t{ id: 1 }` fails with ``expected `shared[t]`, found `&t` `` — the `shared` expression form produces a plain reference — and `shared[T]` has no methods at all, so `.clone()` does not resolve. No atomic reference count exists anywhere. Paired with item 6 (the refcount-reaching-zero drop), this is the other half of [17-shared-ownership-and-drop.md](specification/02-intermediate/17-shared-ownership-and-drop.md).
8. **`scope:` blocks do not parse.** `scope_stmt = "scope" ":" block` is in [kira-grammar.ebnf](kira-grammar.ebnf) line 524 and is referenced normatively by the drop chapter as *the* way to end a binding's lifetime early, but there is no `kw_scope` token and no parser support — `scope:` reports "expected end of line after this". Related to item 2 but distinct: this is the bare lexical scope already in the grammar, not a `with`-style context manager.
9. **`just run` silently loses the standard library.** `bazelisk run //src:kira -- file.kira` runs with the runfiles tree as its working directory, where `find_stdlib_source_file` (`src/driver/driver.cpp:185`) finds none of its candidates. The stdlib is then never injected, so `println` type-checks but fails to lower, and the driver reports ``no concrete checked type is available for this node ... this is a gap in the compiler, not a mistake in your code`` — a confidently wrong diagnostic for correct code, pointing the user at the compiler rather than at their invocation. `./bazel-bin/src/kira file.kira` from the repo root works fine. Either make the runfiles candidate resolve under `bazel run`, or have the driver diagnose a missing stdlib explicitly instead of letting it surface as a bogus lowering gap.
10. **A user module named `s` collides with `std.test`'s internals.** Compiling a file declaring `module s` emits five spurious errors of the form ``module-qualified reference `s.before_all` does not resolve from module `std.test` `` (also `s.cases`, `s.before_each`, `s.after_each`, `s.after_all`). `std.test` evidently uses `s` as a module-qualified binder that resolves against the global module namespace, so any user module of that name shadows it. Renaming the user module to `s2` makes the errors vanish.

11. **A generic `extend`/`impl` block's type parameter could not be used by any call in its own method bodies.** *(Fixed.)* Inside `extend[T] holder[T]`, a call to any generic function — `f(self.v)` or `f[T](self.v)` — was rejected during the *template* pass with "cannot tell what `T` is in this call to `f`" or "`f`'s compile-time argument `T` is not a type this call can name". Both were phase-boundary mistakes: a generic body is checked twice, once abstractly and once per instantiation, and a parameter that is still abstract in the first pass is expected, not wrong. The diagnostics blamed the user and offered a fix ("give it outright in brackets") that does not apply. `check_impl_generic_method_call` already had a `mentions_type_param` bail-out for the *method*-call shape; free generic calls in the same body had no equivalent, which made it impossible to write any generic collection whose methods call helpers — the exact thing `std.list`'s `vector[T]` needed. Fixed by `checker::in_abstract_type_param_scope`, which reports these only once concrete types are in hand.

12. **A module-qualified generic call cannot be monomorphized.** `mem.alloc[int32](4)` — a qualified path with explicit generic arguments — fails with "cannot compile `alloc` for this call: its body uses a construct generic instantiation doesn't support yet ... cannot clone this construct for monomorphization: a method call with generic arguments". The unqualified form (`use std.mem.alloc` then `alloc[int32](4)`) works. `ast_clone` does not handle the qualified-call-with-bracket-arguments shape, so the workaround is to import the name; the two spellings should not differ.

13. **`size_of[T]()` used to type-check and then fail to lower.** *(Fixed.)* It was listed in the prelude and typed as `usize` by the checker, but nothing answered it: `let n = size_of[int32]()` reported "no concrete checked type is available for this node ... this is a gap in the compiler, not a mistake in your code" — the same confidently-wrong diagnostic item 9 describes, for a program that was entirely correct. Both it and the new `align_of[T]()` now fold at lowering time against `runtime::layout_of`, the one function both backends read every field offset and element stride from, so the answer cannot disagree with the stride the type actually occupies.

14. **The bytecode VM allocated straight from the bump arena, bypassing any allocator selection.** *(Fixed.)* `op_alloc` and every `make_*` helper in `src/bytecode/vm.cpp` called `global_arena().allocate` directly, while the LLVM tier went through the `kira_heap_alloc` C-ABI symbol. The two tiers therefore could not be given different allocators, and `KIRA_ALLOCATOR` would have silently applied to only one of them. All 17 call sites now go through `kira_heap_alloc`.

15. **`uninit[T, N]`'s stack storage is capped at 64 KiB per frame** and is not checked against the platform's real stack limit. `op_stack_alloc` encodes its offset as a 16-bit immediate, so a function whose buffers exceed that is refused with an explicit diagnostic rather than miscompiled — but a function *under* that limit can still overflow a small thread stack with no warning, and the LLVM tier (which uses `alloca` and has no such cap) will accept frames the bytecode tier rejects. The two tiers should agree, and the limit should be a real one rather than an encoding artifact.

16. **`list[T]` is still a compiler builtin, and everything it can do is a privilege no user collection has.** `vector[T]` (`src/std/list.kira:83`) is the same data structure written entirely in Kira over `std.mem`, so the library half of the denaturalization is done; what remains is four pieces of compiler knowledge — `list`'s entry in `k_builtin_generic_arities` (`src/semantic/types.cpp:39`), its four entries in `k_builtin_methods` (`src/semantic/check.cpp:205`), `infer_array`'s `expected_is_list` branch (`src/semantic/check.cpp:14154`), and the `list` arm of `resolve_container_view` in both backends. Each is really a missing *language* feature: an `index` trait with an operator hook (indexing is the only core operator with no user-facing trait — `+`/`==` already dispatch through `operator_dispatches`), `for` routed through the already-declared but unused `into_iterator[T]` (`src/std/iter.kira:46`), and array-literal construction through a `from_array` constructor. The plan, with the phase ordering and the drop-glue prerequisite spelled out, is [list-migration-design.md](list-migration-design.md). Phase 4 of it must not land before item 6: flipping `list[T]` onto `malloc`ed storage without scope-exit drop would turn every `[1, 2, 3]` into a silent leak.

17. **A `static def` with generic parameters was never monomorphized.** *(Fixed.)* `check_call_against_decl` gated instantiation on `is_free_function(decl, owner)`, and a `static def` declared in an `extend`/`impl` block is not in `owner->functions` — so a generic one failed that test, was never instantiated, and reached lowering as its uncompiled *template*. Both backends then reported ``call to `trio::from_array` could not be resolved to a function in this compiled module`` — a codegen failure for entirely correct code, of the kind item 9 describes. Reproducible in eight lines with no traits involved: any `static def f[n: usize]` or `static def f[T]` in an `extend` block hit it, while the same signature as a free function worked and the same block's *instance* methods worked. Fixed by admitting `decl.modifiers.is_static` alongside `is_free_function`: a static method takes no receiver, so its instance is named and dispatched exactly like a free function's.

18. **A generic impl method's parameter types were read without the impl block's type parameters in scope, producing silently wrong element widths.** *(Fixed.)* `signature_params` was called without `method->block_type_params` when resolving the element type of a `from_array` impl, so `impl[T] from_array[T] for pair[T]`'s `items: array[T, n]` came back with `T` *abstract* rather than as a type parameter — and `substitute_solved` has nothing to bind an unknown to. An abstract element is laid out at 8 bytes, so the caller wrote a `[10, 20, 30]` of `int32` eight bytes apart while the callee read it four bytes apart: `pair[int32]` came back as `10, 0, 20`. Nothing reported an error. The `int64` case was correct throughout, which is why the regression test covers two element widths — this is exactly the class of bug CLAUDE.md's `# expect:` rule exists for, found by running the program rather than by type-checking it.

19. **`index_mut`, and `cell[T]`/`cell_mut[T]` generally, are implemented end to end on both backends.** *(Fixed.)* `&mut v[i]` on a user type implementing `std.traits.index_mut` resolves and dispatches: `checker::require_index_mut_trait` (`src/semantic/check.cpp`) recognizes the enclosing `&mut` over an `index_expr`, finds `at_mut`, and records the dispatch in `index_mut_dispatches` (parallel to `index_dispatches`/`index_set_dispatches`); `hir::lower_unary` recognizes that dispatch and lowers straight to the `at_mut` call rather than wrapping a `hir_unary(addr_of_mut, ...)` around it; the borrow checker tracks the whole `&mut v[i]` as a mutable view borrow of the receiver via the ordinary `is_view_bearing`/`provenance_of` machinery, since the `index_expr` node is re-recorded with the `cell_mut[T]` type `at_mut` returns. A user type implementing `index` but not `index_mut` gets a dedicated diagnostic pointing at the missing impl.
    The remaining half — `cell[T]`/`cell_mut[T]` had no runtime representation anywhere, so an `at_mut` body had no way to *produce* the `cell_mut[T]` value its signature promised, and the builtin `list.mutable_cell()`/`.cell()` methods this trait was modeled on type-checked but failed at lowering with the same confidently-wrong "no concrete checked type is available for this node" item 9/13 describe — is now closed. `cell[T]`/`cell_mut[T]` are represented exactly like `&T`/`&mut T`: a bare pointer (`is_heap_kind`/`is_heap_type` already gave every `builtin_generic_kind` this shape unconditionally, so no `layout.h` change was needed; `is_heap_pointer_value` in both `codegen.cpp` and `compile.cpp` now lists `cell`/`cell_mut` alongside `slice`/`option`/etc. for the `&`/`*` passthrough). `list.cell(i)` lowers straight to `hir_unary(addr_of, hir_index(...))` and `cell.get()`/`cell_mut.get()` to `hir_unary(deref, ...)` — both reuse the exact address/load machinery plain indexing already had, no new HIR needed. Two new HIR nodes cover what doesn't reduce to an existing shape: `hir_mutable_cell` (`list.mutable_cell(i)`, a bounds-checked `option[cell_mut[T]]` — `@some`/`@none` built by hand, branching around the check instead of `guard_panic`'s/`op_panic_if`'s unconditional trap, since out-of-bounds here means `@none`, not a panic) and `hir_cell_set` (`c.set(v)`, an expression-position store — `hir_assign` is statement-only and has no value of its own for a `.set(...)` call to stand in for). Both are threaded through the two `compile_expr[_into]` switches and the four other exhaustive `hir_node_kind` walkers (`captures.cpp`, `link.cpp`, `live_across_yield.cpp`, `tail_calls.cpp`).
    One more piece an `at_mut` body specifically needs, that `list.cell`/`.mutable_cell` never did: a way to hand back a *field's* address as a `cell_mut[T]`, not a collection element's. `return &mut self.value` used to fail with `expected `cell_mut[_]`, found `&mut int32``, since nothing treated the two as interchangeable even though they are the same runtime pointer. `type_table::compatible` (`src/semantic/types.cpp`) now accepts a `&T`/`&mut T` wherever a `cell[T]`/`cell_mut[T]` is expected (mutability-checked: a plain `&T` cannot satisfy `cell_mut[T]`, which would let `.set(...)` write through a borrow that was never granted exclusively), and `checker::infer_unary`'s `addr_of`/`addr_of_mut` cases type `&expr`/`&mut expr` directly as the expected `cell`/`cell_mut` when one is expected, rather than the mismatched (if compatible) `&T`/`&mut T` — this covers a return, an argument, or a `let` binding, since `expected` threads through `infer_expr` uniformly at every one of those. Regression coverage: `src/testdata/codegen_stress/087_list_cell_and_mutable_cell.kira` (the collection half, `# expect:`-pinned per CLAUDE.md's layout/addressing rule) and `cli_test.cpp`'s `test_run_index_mut_dispatches_to_cell_mut` (the `index_mut`/field-address half, which needs `std.traits` injected and so can't live in `codegen_stress_test`'s single-file corpus) — both run on the bytecode VM and the LLVM AOT tier and assert a computed value, not just a clean compile.
