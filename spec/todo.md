5. DONE. `deriving` now works for **generic** types, for every trait it supports, and `deriving hash` works for concrete and generic types alike. Both halves are covered by `test_run_derives_for_generic_types`/`test_build_derives_for_generic_types` and `test_run_derives_hash_via_deriving_clause` (`src/cli_test.cpp`), the first pair run on both backends.

   **Generic deriving, once per instantiation.** `resolve_deriving_traits` bails on a generic declaration and always will: it runs as a pre-pass, before any instantiation is known, and every `derive_<trait>[T]()` in `src/std/deriving.kira` reflects over a single concrete `T`. Instead `ensure_derived_instance_impls` (`src/semantic/check.cpp`) derives per *instantiation*, lazily, the first time a lookup on it needs a method — keyed on `(type_id, trait)`, never on the declaration, so `wrap[int32]` and `wrap[str]` get separate fragments. Each derived impl registers as if it were a hand-written non-generic `impl` over an applied target (`block_type_params` non-null and empty, `impl_target_pattern` the instantiation), which puts everything downstream on the existing concrete path: `impl_needs_instance` is satisfied, `check_impl_generic_method_call` monomorphizes through `find_or_check_generic_instance`, and `const_generic_instances_` carries the body to lowering. Nothing has to name the applied type syntactically, which is why the derived impl's own `for_type` is left as the derivation wrote it (a bare `wrap`). `find_method` runs the ordinary search *first* and derives only when it finds nothing, so a hand-written `impl show for over[int32]` wins over that type's `deriving show` for free, per instantiation. Const-generic types (`buf[4]` vs `buf[8]`) fall out unchanged, since a derived impl has no type parameters of its own to solve — which is what makes item 8 independent of this rather than a prerequisite.

   Three *other* dispatch sites resolved such a method to the uncompiled template and let lowering compose a name (`wrap::show`) nothing was ever emitted under: string interpolation (`interp_dispatch` — reached by every derived `show` body, since the derivations build their output by interpolation, so this was load-bearing for any nested case like `wrap[wrap[int32]]`), operator overloads (`require_operand_trait`), and `<`/`<=`/`>`/`>=` (`wire_ord_dispatch`). All three now instantiate through `instantiate_impl_method_for`, the call-free sibling of `check_impl_generic_method_call`. `hir::lower_binary` also had to learn the empty-`impl_target_type` convention its three sibling sites already followed; it composed `Type::method` unconditionally and produced a leading `::`.

   `methods_` (and the two builtin-keyed method tables) are `std::deque`, not `std::vector`, and must stay that way: a lookup can now append to the table while a caller holds the `const method_entry *` an earlier lookup returned. Same bug class as `type_table::entries_`.

   **`deriving hash`.** It was held back on the grounds that no builtin scalar implemented `.hash()` and that there was no hash-combining primitive to fold field hashes with; the second half was simply wrong. `*%`/`+%` (wrapping arithmetic, `ast::binary_op::mul_wrap`) are implemented in both backends, and they are exactly what an FNV-1a fold needs — plain `*`/`+` are overflow-checked and panic on the second field. So no new language-level infrastructure was needed: `std.traits` carries real `impl hash` blocks for the builtin scalars (`bool`, `char`, `byte`, `int8`..`int64`, `uint8`..`uint64`, `isize`, `usize`, and a byte-loop one for `str`) plus `hash_seed`/`hash_combine`/`hash_value`/`hash_tag`, and `derive_hash`/`derive_hash_sum` fold with them, all in ordinary Kira. Unlike `ord`, `hash` has no operator dispatching to it, so those scalar impls carry none of the infinite recursion that keeps `impl ord for int32` from existing — see `ord_cmp`. `float32`/`float64` and the 128-bit types are deliberately excluded; see items 7 and 6.

   Still not covered: a derivation that dispatches on a field's *concrete* type. `f.type_name` (`render_type_expr`, `src/comptime/reflect.cpp`) is still syntactic — generic arguments collapse to `"[..]"`, every non-`named_type` shape renders `"<type>"`, aliases are unresolved, and inside a generic declaration a `T` field reports `"T"` rather than the instantiation's type, because `comptime::value`'s type value carries no bindings. None of the five derivations reads `type_name`, so nothing is blocked; the working mechanism for type-dependent behaviour today is `T.name()` in ordinary generic code (`type_param_reflection`), which is how `std.algo`'s `sort[T]` selects a radix sort.
6. `zero`/`one`/`hash` have no impls for the 128-bit types (`int128`, `uint128`, `float128`), because a reachable module is compiled in full and the bytecode VM has no representation for them yet — an `impl zero for int128` in `std.traits` makes every program fail to compile. They arrive with codegen increment 6, alongside the rest of 128-bit support.
7. `hash` has no impls for `float32`/`float64`, so `type p = { x: float64 } deriving hash` type-checks and then reports "no method `hash` on `float64`". Hashing a float correctly means hashing its *bit pattern*, and `as uint64` on a float is a value conversion, not a reinterpret (`compile_cast`, `src/llvm_codegen/codegen.cpp`, emits `FPToUI`) — so this needs a reinterpret/bitcast primitive, which is the rare intrinsic that passes clause (a) of the justification test: it is genuinely inexpressible over the primitive set. Two semantic decisions have to be made explicitly rather than inherited from the bit pattern: `0.0` and `-0.0` compare equal but have different bits, and every NaN compares unequal to itself while there are 2^52 distinct NaN bit patterns — a `hash` that disagrees with `eq` on either is a broken hash.
8. An `impl` block parameterized by a *value* — `impl[n: usize] show for buf[n]` — reports "cannot tell which `n` this call to `show` means". `check_impl_generic_method_call` (`src/semantic/check.cpp`) and `check_impl_generic_static_call` iterate every entry of `block_type_params` and require each to appear in `bindings`, which is a `std::unordered_map<std::string, type_id>` populated by `unify_rigid` and so cannot hold a value binding at all. Needs the `value_bindings` channel `solve_generic_params` already uses for free functions extended to impl blocks, plus an instance suffix that distinguishes `buf[4]` from `buf[8]` (`mangle_type_for_instance` may already separate them — verify rather than assume, since a collision there silently compiles one body for both). The diagnostic is also the wrong shape for this case: it blames the user's call site and suggests moving `n` onto the method, for a parameter the receiver plainly determines.
9. `!=` inside a string interpolation fails to parse: `println("{a.hash() != b.hash()}")` reports "unexpected `!` — Kira uses `not` for logical negation, not `!`", pointing at the `!` of a `!=` the lexer handles correctly everywhere else. `==` in the same position is fine, and hoisting the comparison into a `let` is the workaround. The interpolation scanner appears to re-lex the segment without the two-character-operator handling the main lexer has, so the diagnostic is also actively misleading — it names a rule the user did not break.
