Full Unicode case mapping and folding for `std.string` are done (`std.unicode`/`std.unicode_tables`, pure Kira over generated UCD tables — see [52-std-string.md](specification/04-stdlib/strings-and-formatting/52-std-string.md)). Still deferred, each needing more work than "read another generated table": locale-tailored casing (Turkish/Azeri dotted/dotless-I, Lithuanian dot-retention — needs a locale parameter threaded through every casing call), NFC/NFD normalization, and grapheme-cluster segmentation (UAX #29) so `reversed`/`split` can operate on graphemes rather than scalars.
2. "with" style scoped blocks.
3. store and load binary AST instead of reparsing
4. store and load generated bytecode instead of recompiling
5. A derivation that dispatches on a field's *concrete* type. `f.type_name` (`render_type_expr`, `src/comptime/reflect.cpp`) is still syntactic — generic arguments collapse to `"[..]"`, every non-`named_type` shape renders `"<type>"`, aliases are unresolved, and inside a generic declaration a `T` field reports `"T"` rather than the instantiation's type, because `comptime::value`'s type value carries no bindings. None of the five derivations reads `type_name`, so nothing is blocked; the working mechanism for type-dependent behaviour today is `T.name()` in ordinary generic code (`type_param_reflection`), which is how `std.algo`'s `sort[T]` selects a radix sort.
6. `zero`/`one`/`hash` have no impls for the 128-bit types (`int128`, `uint128`, `float128`), because a reachable module is compiled in full and the bytecode VM has no representation for them yet — an `impl zero for int128` in `std.traits` makes every program fail to compile. They arrive with codegen increment 6, alongside the rest of 128-bit support.
7. `deriving hash`  does not lower through the HIR/LLVM tier at all yet — `a.hash()` on any `deriving hash` type fails HIR lowering with "no concrete checked type is available for this node" — so this fix, like the rest of `deriving hash`, is exercised only via the tier-0 bytecode VM (`cli_test.cpp`'s `run` mode), not `codegen_stress_test`.
8. A call to a `static def` from ordinary (non-`static`) runtime code never lowers — `checker::register_comptime_globals` marks every free top-level `static def` as compile-time-only (`comptime_only_functions_`), and `hir::lower.cpp`'s const-generic-instance loop correctly skips lowering it, but there is no mechanism that instead constant-folds the *whole call* when it's reached from ordinary code with a concrete type argument. A call from `static assert`/`static if`/another `static def`'s own body works fine (the comptime evaluator handles it directly); a call from an ordinary generic function's body fails at HIR lowering with `` call to `foo$T` could not be resolved to a function in this compiled module ``. Confirmed both with a minimal repro and in real stdlib: `std.traits.is_struct`/`is_sum`/`type_category`/`is_convertible` are `static pure def`s (needed for `T.kind()`/`implements`) and are therefore usable only from `static` contexts today, not from an ordinary generic body, despite [58-std-traits.md](specification/04-stdlib/type-traits/58-std-traits.md)'s own text describing them as usable anywhere a compile-time `bool` is. Every predicate in `std.traits`/`std.limits` that doesn't strictly need `T.kind()` was written as a plain (non-`static`) `def` dispatching on `T.name()` instead, specifically to route around this gap.
9. A `static def` can only directly call *other* `static def`s from within its own body — calling an ordinary (non-`static`) function from inside a `static def`'s body fails with `` only direct calls to a named `static def` function are supported in compile-time evaluation ``. This is why `std.traits.type_category`/`is_convertible` inline their `T.name()`/`T.kind()` logic rather than delegating to `is_bool`/`is_signed_integer`/`is_same`.
10. Every branch of an ordinary `if`-chain type-checks against the same concrete `T`, even when `T.name()` guarantees only one branch is ever reached for that `T` — so `if n == "int64": return SOME_INT64_LITERAL as T` fails for `T = int32` even though that branch is dead for `int32`, because the literal must fit *every* `T` the function is ever instantiated at. `static if` can't help either: its branch bodies only accept declarations, never statements (`return`/an assignment), a gap [31-compile-time-execution.md](specification/03-advanced/31-compile-time-execution.md) already documents ("contrary to an earlier version of this section's claim"). Worked around in `std.limits.min`/`max` by accumulating into one fixed-width local (`var v: int64`/`var v: uint64`) across every branch and casting to `T` only once, in the final `return`.
11. The most-negative integer literal for a width can't be written directly — `-9223372036854775808` (`int64::MIN`) is rejected as "too large for `int64`", because the literal's positive magnitude is validated before unary `-` is applied, and `9223372036854775808` is one past `int64::MAX`. Write `-9223372036854775807 - 1` instead (the same trick works at any width).
12. Formatting exactly `int64::MIN` via string interpolation panics with "integer overflow" at runtime, even though arithmetic/comparison against that exact value works fine — looks like a classic `abs(INT64_MIN)` overflow in the int-to-string formatting path (`src/runtime/fmt.*` or the bytecode VM's equivalent).
13. A real, currently unfixed, apparently nondeterministic bug: two or more top-level `static def`s in the same module, each containing a `match` on a sum-type value, can intermittently break each other's variant-tag resolution — `` `<variant-name>` is not a compile-time constant that has been evaluated yet ``, rooted in `checker::resolve_variant_tag`'s `node_types_.find(&node)` lookup. Confirmed nondeterministic: the exact same unmodified file, recompiled repeatedly with `kira-out/` deleted each time, sometimes succeeds and sometimes fails — suggests pointer-hash/`unordered_map`-iteration-order sensitivity (ASLR) somewhere in the checker's declaration-registration order, not a logic bug tied to any specific name. `std.traits.is_struct`/`is_sum`/`type_category` all contain `match T.kind():` and coexist in one module, so this is a live risk for that file, not just a theoretical one.
