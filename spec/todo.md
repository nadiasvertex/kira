1. Full Unicode case mapping and folding for `std.string` are done (pure Kira over generated UCD tables — see [52-std-string.md](specification/04-stdlib/strings-and-formatting/52-std-string.md)). Still deferred: locale-tailored casing (Turkish/Azeri, Lithuanian — needs a locale parameter threaded through every casing call), NFC/NFD normalization, and grapheme-cluster segmentation (UAX #29) so `reversed`/`split` operate on graphemes rather than scalars.
2. "with" style scoped blocks.
3. Store and load binary AST instead of reparsing.
4. Store and load generated bytecode instead of recompiling.
5. `zero`/`one`/`hash` have no impls for the 128-bit types (`int128`, `uint128`, `float128`): a reachable module is compiled in full and the bytecode VM has no representation for them yet, so an `impl zero for int128` in `std.traits` would break every program. They arrive with codegen increment 6.
6. **Scope-exit `drop`: done for the common case, with deliberate gaps.** `checker::resolve_drop_plans` (`src/semantic/check.cpp`) and `hir::compute_drop_schedule` (`src/hir/drop_schedule.{h,cpp}`) schedule reverse-declaration-order drop calls at scope exit and at `return`/`break`/`continue`; `hir::lowerer` synthesizes the `hir_call`s — an ordinary function call, so no new backend code. Verified on both backends: `src/testdata/std_test/scope_exit_drop.kira`; direct `x.drop()` is rejected (`src/testdata/semantic_check_test/reject_direct_drop_call.kira`). `compute_drop_schedule` is a second walker alongside `move_check` (not a replacement).
   Remaining gaps, each left deliberately:
   - A block/function whose tail is a non-`unit` value skips scope-exit drop for that scope entirely (a leak, never a double-drop) — needs a temporary-materialization pass.
   - Locals a `return expr` merely borrows from are never dropped (the read happens as part of compiling the return); a local `return`ed directly is unaffected.
   - Match-arm, `for`-loop, and destructuring pattern bindings are not tracked — only plain `let`/`var` and simple parameters are; the current `for`-loop desugaring routes its loop variable through exactly this untracked path.
   - Sum-type field-wise drop is not implemented; only the sum's own `impl drop` runs.
   - Unwinding through drops on panic is moot: there is no stack unwinding (`panic`/`assert` compile to a trap).
   - No prelude `drop(x)` free function exists: bare `drop(x)` is accepted by the checker, then fails in lowering with a confidently wrong "no concrete checked type" diagnostic for what is really an unresolved name.
   `spec/list-migration-design.md`'s phase 4 needs only reverse-order drop, moved-from exclusion, and struct field-wise drop from this item — all three hold for the common case it will exercise.
7. **`shared[T]` is a name with nothing behind it.** Registered as a builtin generic (`src/semantic/types.cpp:51`) and that is the whole implementation: the `shared` expression form produces a plain reference, `shared[T]` has no methods, and no atomic reference count exists. Paired with item 6, this is the other half of [17-shared-ownership-and-drop.md](specification/02-intermediate/17-shared-ownership-and-drop.md).
8. **`scope:` blocks do not parse.** `scope_stmt = "scope" ":" block` is in [kira-grammar.ebnf](kira-grammar.ebnf) line 524 and is the drop chapter's normative way to end a binding's lifetime early, but there is no `kw_scope` token or parser support. Related to item 2 but distinct: this is the bare lexical scope, not a `with`-style context manager.
9. **`just run` silently loses the standard library.** `bazelisk run //src:kira -- file.kira` runs with the runfiles tree as cwd, where `find_stdlib_source_file` (`src/driver/driver.cpp:185`) finds no candidates, so the stdlib is never injected and `println` fails to lower with a confidently wrong "gap in the compiler" diagnostic. `./bazel-bin/src/kira file.kira` from the repo root works. Either make the runfiles candidate resolve under `bazel run`, or diagnose a missing stdlib explicitly.
10. **A user module named `s` collides with `std.test`'s internals.** `module s` emits five spurious "module-qualified reference `s.*` does not resolve" errors (also `s.cases`, `s.before_each`, etc.); renaming to `s2` makes them vanish. `std.test` uses `s` as a module-qualified binder against the global namespace, so any user module of that name shadows it.
12. **A module-qualified generic call cannot be monomorphized.** `mem.alloc[int32](4)` fails ("cannot clone this construct ... a method call with generic arguments") because `ast_clone` does not handle the qualified-call-with-bracket-arguments shape; the unqualified form (`use std.mem.alloc` then `alloc[int32](4)`) works. The two spellings should not differ.
15. **`uninit[T, N]`'s stack storage is capped at 64 KiB per frame** because `op_stack_alloc` encodes its offset as a 16-bit immediate — an encoding artifact, not a real platform limit. A function under the cap can still overflow a small thread stack with no warning, and the LLVM tier (`alloca`) has no such cap. The two tiers should agree, and the limit should be real.
16. **`list[T]` is a library type now; the sweep behind it is unfinished.** `list[T]` is an ordinary generic struct in `src/std/list.kira` (Kira over `std.mem`/`machine`), reaching the language through the same `std.traits` + `std.iter` traits any user collection implements; it is gone from `k_builtin_generic_arities` and `k_builtin_methods`, and `range[T]` followed. What remains of [list-migration-design.md](list-migration-design.md)'s phase 4 is items 17-20 below, plus now-dead compiler code: `is_list_type`/`resolve_container_view`'s `list` arm in **both** backends (`src/bytecode_compiler/compile.cpp:1025`, `src/llvm_codegen/codegen.cpp:980` — each tests `builtin_generic_kind`, which `list` no longer is, so the arms can never fire) and `list_reserve_slot` with its LLVM declaration (`src/llvm_codegen/codegen.h:86`). The pre-flip benchmark (sort 100k `int32`, both tiers, both allocator modes) was never taken; every `list` index is a real call now and there is no number saying what that costs.
17. ~~A read-borrow of an element, `&v[i]`, has no route on a user collection.~~ *(Fixed.)* `std.traits` gained `index_ref[I] requires index[I]` with `at_ref(self, i: I) -> cell[self.output]` (`src/std/traits.index.kira`); `list[T]` implements it for `usize`. `checker::infer_unary` re-dispatches `&v[i]` against `index_ref` (guarded to skip range-index reads, which are already complete `slice[T]` values), and `hir::lower_unary` lowers it straight to `at_ref`. Fixing this surfaced the missing reverse direction in `type_table::compatible`: a `cell[T]`/`cell_mut[T]` result did not satisfy an `&T`/`&mut T` context (e.g. `std.iter`'s borrowing iterators, `src/std/iter.kira:142`); only the opposite direction existed. With it, the five previously failing std tests (`iter_adapters_{compose,nesting,pairing,slicing}.kira`, `compound_where_bound.kira`) compile and run on both tiers.
18. ~~A `list[T]` parameter in `std.io` degrades to the bare constructor `list`, depending on the compile entry point.~~ *(Fixed.)* Not a name-resolution bug: `checker::build_method_table` set its one-shot `methods_built_` guard *before* finishing, then monomorphized trait defaults inline, which can reentrantly call back into `build_method_table` and see a partially built table — order-dependent on which module is the entry point. Fixed by splitting into two passes: register all methods first, then monomorphize the deferred trait defaults once that is complete.
    Fixing this surfaced a second, distinct bug: `//src:cli_test`'s `test_run_index_mut_dispatches_to_cell_mut` is stale (still declares `index_mut`'s old `type output = int32` shape), and once corrected fails only when run after enough other tests in the same process — something order- or allocation-history-dependent makes `require_index_mut_trait`'s dispatch entry go unseen by `hir::lower_unary`, falling through to "cannot take the address of this expression". Needs isolating what state leaks across `compile_sources` calls within one process.

20. **Empty `[]` needs an annotation — closed.** `var xs = []` is now pinned by a later use (`xs.push(v)`, a return, an argument), in concrete code and in generic bodies alike: the standard library's `partition` and `from_iter` build their lists from an unannotated `[]`. Done by `spec/inference-rewrite.md` phases 8 and 9 — the literal mints a metavariable and the solving happens where a value already meets a declared type, so nothing re-solves anything. A literal nothing ever says anything about is still refused, now against its own line rather than against `src/std/list.kira`'s internals. Unannotated parameters are now leaves too (`param_usage_inferrer` is deleted) and, when the body leaves one open, implicit generics compiled once per call type (`spec/inference-rewrite.md` phase 8b). Remaining: methods in `impl`/`extend` blocks with such a parameter, and an unannotated return type in lowering.

21. ~~A borrow of a number could be used as the number, and the address was used instead.~~ *(Fixed.)* `def read(v: &int32) -> int32: return v` compiled, and returned the *address*. So did `v + 1`, and so did `for v in xs.iter(): total = total + v` — which is how this was found: that loop returned 4, 68, 100 or 196 depending on the run, never 16. A silently wrong answer on fully annotated, concrete code.

    The rule the compiler was missing is the one `codegen_stress/042` already states: a `&` to an aggregate is free, because a `list`/`str`/tuple/struct/sum/closure value *is* an address already and `xs.len()` through a `&list[T]` is the same code as through an owned one; a `&` to a number *materializes* an address, and reading the number back out is a load, spelled `*`. Typing knew only the first half — `type_table::compatible` accepted any `&T` wherever `T` was expected, and `infer_binary` ran `base_shape` over its operands — so nothing ever asked for the load.

    Now one predicate answers it in one place: `type_table::is_heap_represented` (what `llvm_codegen`'s `is_heap_type` is defined as) and `reference_is_transparent` on top of it, which adds the still-abstract referents — `&T` in a generic body — where the question cannot be answered until instantiation. A `&number` used as the number is refused at both sites, with a diagnostic that names the fix rather than observing that two spellings differ.

    Both backends produced the same wrong answer, so `codegen_stress_test`'s cross-tier agreement was perfectly satisfied — the case CLAUDE.md's note on differential tests describes. The regression test (`codegen_stress/094_borrowed_element_needs_a_load.kira`) asserts the sum with `# expect:`, and contrasts all three forms: `for v in xs.iter()` needs the `*`, `for v in xs` does not, and `xs.len()` through a `&list[int32]` costs nothing.

    Two things this does *not* do. `for x in &xs` still yields `&T` and so still needs `*x` — `std.iter`'s `values()` adapter exists precisely to spare a chain from spelling it — and `accept_for_over_ref_borrow.kira` was updated accordingly; that fixture asserts only the absence of borrow-check diagnostics, and the form does not lower end to end at all. And a `&T` whose `T` is still a type parameter is let through, so the same mistake inside a generic body is caught only when the body is instantiated.
