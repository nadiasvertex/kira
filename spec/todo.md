1. Full Unicode case mapping and folding for `std.string` are done (pure Cinder over generated UCD tables — see [52-std-string.md](specification/04-stdlib/strings-and-formatting/52-std-string.md)). Still deferred: locale-tailored casing (Turkish/Azeri, Lithuanian — needs a locale parameter threaded through every casing call), NFC/NFD normalization, and grapheme-cluster segmentation (UAX #29) so `reversed`/`split` operate on graphemes rather than scalars.
2. "with" style scoped blocks.
3. Store and load binary AST instead of reparsing.
4. Store and load generated bytecode instead of recompiling.
5. `zero`/`one`/`hash` have no impls for the 128-bit types (`int128`, `uint128`, `float128`): a reachable module is compiled in full and the bytecode VM has no representation for them yet, so an `impl zero for int128` in `std.traits` would break every program. They arrive with codegen increment 6.
6. **Scope-exit `drop`: done for the common case, with deliberate gaps.** `checker::resolve_drop_plans` (`src/semantic/check.cpp`) and `hir::compute_drop_schedule` (`src/hir/drop_schedule.{h,cpp}`) schedule reverse-declaration-order drop calls at scope exit and at `return`/`break`/`continue`; `hir::lowerer` synthesizes the `hir_call`s — an ordinary function call, so no new backend code. Verified on both backends: `src/testdata/std_test/scope_exit_drop.cn`; direct `x.drop()` is rejected (`src/testdata/semantic_check_test/reject_direct_drop_call.cn`). `compute_drop_schedule` is a second walker alongside `move_check` (not a replacement).
   Remaining gaps, each left deliberately:
   - A block/function whose tail is a non-`unit` value skips scope-exit drop for that scope entirely (a leak, never a double-drop) — needs a temporary-materialization pass.
   - Locals a `return expr` merely borrows from are never dropped (the read happens as part of compiling the return); a local `return`ed directly is unaffected.
   - Match-arm, `for`-loop, and destructuring pattern bindings are not tracked — only plain `let`/`var` and simple parameters are; the current `for`-loop desugaring routes its loop variable through exactly this untracked path.
   - Sum-type field-wise drop is not implemented; only the sum's own `impl drop` runs.
   - Unwinding through drops on panic is moot: there is no stack unwinding (`panic`/`assert` compile to a trap).
   - No prelude `drop(x)` free function exists: bare `drop(x)` is accepted by the checker, then fails in lowering with a confidently wrong "no concrete checked type" diagnostic for what is really an unresolved name.
   `spec/list-migration-design.md`'s phase 4 needs only reverse-order drop, moved-from exclusion, and struct field-wise drop from this item — all three hold for the common case it will exercise.
7. **`shared[T]` is a name with nothing behind it.** Registered as a builtin generic (`src/semantic/types.cpp:51`) and that is the whole implementation: the `shared` expression form produces a plain reference, `shared[T]` has no methods, and no atomic reference count exists. Paired with item 6, this is the other half of [17-shared-ownership-and-drop.md](specification/02-intermediate/17-shared-ownership-and-drop.md).
8. **`scope:` blocks do not parse.** `scope_stmt = "scope" ":" block` is in [cinder-grammar.ebnf](cinder-grammar.ebnf) line 524 and is the drop chapter's normative way to end a binding's lifetime early, but there is no `kw_scope` token or parser support. Related to item 2 but distinct: this is the bare lexical scope, not a `with`-style context manager.
9. **`just run` silently loses the standard library.** `bazelisk run //src:cinder -- file.cn` runs with the runfiles tree as cwd, where `find_stdlib_source_file` (`src/driver/driver.cpp:185`) finds no candidates, so the stdlib is never injected and `println` fails to lower with a confidently wrong "gap in the compiler" diagnostic. `./bazel-bin/src/cinder file.cn` from the repo root works. Either make the runfiles candidate resolve under `bazel run`, or diagnose a missing stdlib explicitly.
11. **A struct-valued `static` has no runtime storage.** `static let origin: point = ...` is usable at compile time and its scalar fields fold to constants (`origin.x`), but `let p = origin` or `origin.a` (a struct field) fails in lowering — the bytecode compiler's message ("a bare function value used outside of call position is not supported yet") is confidently wrong. Only arrays/lists of scalars are reified as globals (`reify_static_global`).
12. **The compile-time evaluator has no loops.** `while` and `for` inside a function evaluated at compile time (e.g. `static X: int64 = fib(50)` where `fib` loops) fall to the `default` case of `evaluate_stmt` in `src/comptime/eval.cpp` ("this statement form is not yet supported in compile-time evaluation"). [31-compile-time-execution.md](specification/03-advanced/31-compile-time-execution.md) promises "the same functions, loops, and pattern matching"; recursion works today, loops don't. The failure also cascades: the bytecode stage then reports `` reference to `X` is not a local binding — a bare function value used outside of call position is not supported yet `` for the scalar `static`, the same confidently wrong message as item 11. A failed `static` initializer should stop lowering from ever seeing the binding.
13. **Refinement refutation names the wrong conjunct.** With `type percent = int32 where self >= 0 and self <= 100`, `show(250)` is reported as `` `250 >= 0` is never true here `` — true, and not the reason. The conjunct actually refuted is `250 <= 100`. The diagnostic must name the conjunct the solver refuted, not the first one.
16. **The result of an implicit generic is not typed by a later use.** For `def add_one(x): x + 1`, `let r = add_one(5)` then `let c: int64 = r` reports `` expected `int64`, found `int32` ``: the instance for the `5` is chosen before the annotation is read. `let a = 5; let c: int64 = a` works, so this is the implicit-generic call path choosing early, not literal defaulting. Found during [inference-rewrite.md](inference-rewrite.md) phase 11.
17. **`bool + bool` is not diagnosed.** `let a = true; let s = a + a` type-checks and then fails in lowering with "no concrete checked type is available for this node" — a confidently wrong "gap in the compiler" for a user mistake. `require_operand_trait` on a builtin with no operator impl answers `unknown` silently instead of "operator `+` requires numeric operands, found `bool`". The deferred check for an operand that settles later (`defer_open_arithmetic`) inherits the same silence.
