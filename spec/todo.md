5. `deriving` produces no runnable method body for a **generic** type, for any of its traits. `resolve_deriving_traits` (`src/semantic/check.cpp`) only splices a real `derive_<trait>[T]()`/`derive_<trait>_sum[T]()` in for a concrete type (`!decl.type_params.empty()` still bails out immediately), because every derivation in `src/std/deriving.kira` needs a single concrete `T` to reflect over via `T.fields()`/`T.variants()`; a generic `type box[T] = { value: T } deriving show` stays on the type-check-only `derived_method_result` path, so `b.show()` type-checks and then fails lowering with "no concrete checked type is available for this node". The fix is the same shape `const-generic-monomorphization`/`type-generic-monomorphization` already used for ordinary generic functions: run derivation once per concrete instantiation instead of at the generic declaration. (Sum-shaped deriving is done: `derive_show_sum`/`derive_eq_sum`/`derive_debug_sum`/`derive_ord_sum` build one `match` per method over `T.variants()` — reflection added to `reflect.cpp`, gated on `sum_type_def` symmetrically with the struct-only `fields()`/`field_count()` — via three new AST-builder intrinsics, `expr.ctor_pattern`/`expr.match_on`/`expr.arm` (`src/comptime/eval.cpp`; `match` itself is a keyword so the builder is spelled `match_on`), which is the statement/match-arm construction the struct derivations' own doc comments said was missing. `resolve_deriving_traits` now checks `comptime_eval_.has_pending_function(...)` before attempting a derive call, so a test harness that doesn't inject `std.derive` (several existing fixture sets don't) degrades to the type-check-only path exactly as before, instead of leaking a real "only direct calls..." diagnostic — this was a latent gap in the struct path too, just never previously exercised by an existing fixture.) `deriving hash` is the one *struct* trait still on the type-check-only path: no builtin scalar implements `.hash()`, and there is no hash-combining primitive to fold field hashes with, so it needs new language-level infrastructure rather than just new derive logic. (`deriving ord` itself is done for concrete struct and sum types: `derive_ord`/`derive_ord_sum` fold the fields/variants into a lexicographic chain of `std.traits`' `ord_cmp`/`ord_then`/`ord_less`/`ord_greater`, spliced in like `show`/`eq`/`debug`. `ord_cmp` compares with `<` rather than recursing through `.cmp()` deliberately — an `impl ord for int32` would define the very `cmp` that `<` dispatches to on that type, and `<` inside its body would then call itself forever, so the primitives keep their native comparison codegen and need no impls of their own.)
6. `zero`/`one` have no impls for the 128-bit types (`int128`, `uint128`, `float128`), because a reachable module is compiled in full and the bytecode VM has no representation for them yet — an `impl zero for int128` in `std.traits` makes every program fail to compile. They arrive with codegen increment 6, alongside the rest of 128-bit support.
