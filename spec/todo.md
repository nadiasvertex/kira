Full Unicode case mapping and folding for `std.string` are done (`std.unicode`/`std.unicode_tables`, pure Kira over generated UCD tables — see [52-std-string.md](specification/04-stdlib/strings-and-formatting/52-std-string.md)). Still deferred, each needing more work than "read another generated table": locale-tailored casing (Turkish/Azeri dotted/dotless-I, Lithuanian dot-retention — needs a locale parameter threaded through every casing call), NFC/NFD normalization, and grapheme-cluster segmentation (UAX #29) so `reversed`/`split` can operate on graphemes rather than scalars.
9. `for c in s` over a `str` does not decode UTF-8 — `str` has no `next(mut self)` for the general user-iterator desugaring, so it falls through to the byte-indexed `hir::lowerer::lower_indexed_loop` (the same shape `array`/`list`/`slice` use), yielding raw bytes cast to `char` rather than decoded scalars. Contradicts 52-std-string.md's and `std.unicode`'s original design's assumption that `for`-loop iteration over `str` yields scalars; confirmed by `for c in "straße": println(c as uint32)` printing `ß`'s two continuation bytes (195, 159) instead of 223. `std.unicode` works around it by decoding UTF-8 by hand over `str.as_bytes()`. Needs new HIR-lowering machinery (a dedicated str-loop shape doing real byte-cursor UTF-8 decoding), not a one-line fix.
10. `\u{XXXX}` string escapes mis-trigger the interpolation scanner. `has_interpolation`/`scan_interpolated_content` (`src/parser/interp_string.cpp`) skip exactly one character past a backslash for every escape — correct for `\n`/`\"`/etc., wrong for the variable-width `\u{...}` escape, whose `{` gets mistaken for a real interpolation hole's start. Any string literal containing `\u{...}` fails to parse (as an "invalid escape sequence" or an unterminated interpolation, depending on what follows). Found while writing `std.unicode`'s tests, worked around there by typing non-ASCII characters directly as UTF-8 instead of via the escape.

5. `deriving ord` type-checks but `cmp` does not lower: `a.cmp(b)` on a `deriving ord` type fails with "no concrete checked type is available for this node". `ord` is deliberately excluded from `k_real_derive_traits` (`src/semantic/check.cpp`) and stays on the type-check-only `derived_method_result` path. Its return type `ordering` is now a real sum type, so the remaining work is a real derived `cmp` — a lexicographic field-by-field comparison — which also needs `ord` impls for the primitive field types.
6. A compound bound in a `where` clause cannot be cloned for monomorphization. `def sum[I, T](it: I) -> T where I: iterator[T], T: add + zero` reports "cannot clone this construct for monomorphization: this type-expression shape" pointing at `add + zero`; splitting it to a single bound compiles. `std.algo`'s `sum` and `product` are written `T: zero` and `T: one` for this reason rather than the `T: add + zero` / `T: mul + one` design §6.1 specifies.
7. `zero`/`one` have no impls for the 128-bit types (`int128`, `uint128`, `float128`), because a reachable module is compiled in full and the bytecode VM has no representation for them yet — an `impl zero for int128` in `std.traits` makes every program fail to compile. They arrive with codegen increment 6, alongside the rest of 128-bit support.
8. `let (a, b) = x`/`match x: (a, b) => ...` where `x` is a plain multi-name statement destructure of a fixed `array[T, N]` (not a tuple) has no codegen-level test coverage for narrow `T` — `hir_tuple_index` is reused for both tuple-element and array-element projection (`src/hir/nodes.h`'s own doc comment on `hir_tuple_index`), and only the tuple side was exercised end-to-end before this was checked while fixing item 6 above. Both backends' `compile_tuple_index` do branch correctly on `object`'s type kind today, but a regression here would currently go undetected by any test.
