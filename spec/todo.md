1. Tail call optimization
2. Full Unicode support for `std.string` (spec/std-reference.md ships Unicode *simple* 1:1 case mapping only). Deferred: full/special case mapping (`ß`→`SS`, final-sigma, locale-tailored Turkish/Azeri/Lithuanian), case folding for caseless comparison, NFC/NFD normalization, and grapheme-cluster segmentation (UAX #29) so `reversed`/`split` can operate on graphemes rather than scalars. Each needs additional generated Unicode tables.
3. "with" style scoped blocks.
4. store and load binary AST instead of reparsing
5. store and load generated bytecode instead of recompiling
6. `deriving ord` type-checks but `cmp` does not lower: `a.cmp(b)` on a `deriving ord` type fails with "no concrete checked type is available for this node". `ord` is deliberately excluded from `k_real_derive_traits` (`src/semantic/check.cpp`) and stays on the type-check-only `derived_method_result` path. Its return type `ordering` is now a real sum type, so the remaining work is a real derived `cmp` — a lexicographic field-by-field comparison — which also needs `ord` impls for the primitive field types.
7. A compound bound in a `where` clause cannot be cloned for monomorphization. `def sum[I, T](it: I) -> T where I: iterator[T], T: add + zero` reports "cannot clone this construct for monomorphization: this type-expression shape" pointing at `add + zero`; splitting it to a single bound compiles. `std.algo`'s `sum` and `product` are written `T: zero` and `T: one` for this reason rather than the `T: add + zero` / `T: mul + one` design §6.1 specifies.
8. A lambda capturing a mutable local collection does not lower. `var seen: list[int32] = []` followed by `xs.into_iter().for_each((x) => seen.push(x * 2))` type-checks and then fails with "no concrete checked type is available for this node" pointing at `seen.push`. Found while testing `for_each`, whose only observable effect is a capture.
9. `zero`/`one` have no impls for the 128-bit types (`int128`, `uint128`, `float128`), because a reachable module is compiled in full and the bytecode VM has no representation for them yet — an `impl zero for int128` in `std.traits` makes every program fail to compile. They arrive with codegen increment 6, alongside the rest of 128-bit support.
10. `let (a, b) = x`/`match x: (a, b) => ...` where `x` is a plain multi-name statement destructure of a fixed `array[T, N]` (not a tuple) has no codegen-level test coverage for narrow `T` — `hir_tuple_index` is reused for both tuple-element and array-element projection (`src/hir/nodes.h`'s own doc comment on `hir_tuple_index`), and only the tuple side was exercised end-to-end before this was checked while fixing item 6 above. Both backends' `compile_tuple_index` do branch correctly on `object`'s type kind today, but a regression here would currently go undetected by any test.
11. A parser bug: a `var`/`if`/other non-`let` statement immediately before a `let x = match ...:`/`let x: T = match ...:` statement (whose arms span multiple indented lines) causes the *following* statement to be misparsed as an `if`-*expression* ("expected `else` in conditional expression"), even though the same `let ... = match ...:` is fine as the first or second statement in a block, or with only other `let`s before it. Found while writing a regression test for item 6's fix; reproduces with as little as `let t = ...` / `var score = 0` / `let m = match t: ... ` / `if m == ...:`.
