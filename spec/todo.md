3. store and load binary AST instead of reparsing
4. store and load generated bytecode instead of recompiling
5. `deriving` produces no runnable method body for a **sum-shaped or generic** type — for any of its traits, not just `ord`. `resolve_deriving_traits` (`src/semantic/check.cpp`) only splices a real `derive_<trait>[T]()` in for a concrete, struct-shaped type, because every derivation in `src/std/deriving.kira` is written against `T.fields()`; anything else stays on the type-check-only `derived_method_result` path, so `c.show()`/`c.cmp(&d)` on a `type color = @red | @green deriving show, ord` type-checks and then fails lowering with "no concrete checked type is available for this node". A sum derivation needs variant reflection (`T.variants()`, with each variant's payload types) and a way to generate a `match` — the AST builders construct expressions only, and there is no statement or match-arm builder. `deriving hash` is the one *struct* trait still on that path: no builtin scalar implements `.hash()`, and there is no hash-combining primitive to fold field hashes with, so it needs new language-level infrastructure rather than just new derive logic. (`deriving ord` itself is done for concrete struct types: `derive_ord` folds the fields into a lexicographic chain of `std.traits`' `ord_cmp`/`ord_then`, spliced in like `show`/`eq`/`debug`. `ord_cmp` compares with `<` rather than recursing through `.cmp()` deliberately — an `impl ord for int32` would define the very `cmp` that `<` dispatches to on that type, and `<` inside its body would then call itself forever, so the primitives keep their native comparison codegen and need no impls of their own.)
6. `zero`/`one` have no impls for the 128-bit types (`int128`, `uint128`, `float128`), because a reachable module is compiled in full and the bytecode VM has no representation for them yet — an `impl zero for int128` in `std.traits` makes every program fail to compile. They arrive with codegen increment 6, alongside the rest of 128-bit support.
