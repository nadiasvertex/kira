# Unified type checker plan

Status: accepted, 2026-11-15. Phases 1 to 3 are complete; phase 3 finished on 2026-11-19. Phase 4 is in progress: its done-when programs pass (2026-11-20), and two debts remain.

The type-checking bugs in [todo.md](todo.md) share three structural causes. The checker
hands later stages about 85 side tables keyed by AST node, and each later stage decides
again what it accepts. The checker has several parallel paths for the same construct, so a
fix to one path leaves the others wrong. The ownership check is a separate analysis over
the AST that does not see generated code and tracks borrows per whole variable.

This plan replaces the side tables with one typed core program that the checker emits,
adds an independent verifier for that core, and gives each construct (call, place, pattern,
type equality) one implementation. The ownership check then runs over the core with
field-level places and inferred function summaries. The work is twelve phases; each lands with
all tests passing. The plan is self-contained: it defines the ownership rules it needs and
does not depend on the affine-capability designs. It closes 28 of the 34 open todo items.
The six items left out are not checker problems.

## Causes

Each open item traces to one of three causes.

**Stages disagree about what a valid program is.** The checker records its decisions in
side tables. Ownership checking, HIR lowering, storage lowering, and both backends each
walk the AST again and read those tables. HIR lowering has about 150 places where it can
refuse a program, storage lowering and its verifier about 250, and each backend about 50.
A program the checker accepts can fail in any of them, with a message written for compiler
authors. Compile-time code reads a second copy of the tables (the lowering view), which can
omit a record the first copy has. Items 9, 15, 22, 25, 26, 27, 29, 36, and 37 are of this
kind.

**One construct has several implementations.** The checker has 17 entry points for
checking a call. A bare call binds explicit type arguments and a module-qualified call
does not (item 8). A static method through a bound works and the same method on a builtin
type does not (item 9). A method call on a pattern binding and an assignment to it follow
different mutability rules (item 21). `&mut xs[i]` produces a view type and `&mut x`
produces a reference (items 33 and 38). A `usize` type index is compared and a `bool` index is
not (item 32). A trait can be queried with `implements` and a concept cannot (item 14).
A user variant named `@ok` resolves to the prelude's in one path and to the user's in
another (item 35).

**Ownership is checked beside the program, not on it.** The ownership check builds its own
control-flow graph from the AST. It walks each file's own items, so it skips impls
generated by `deriving` and splices (item 23). It compares borrows per whole variable. Its
rule for calls does not model a callee storing a borrow into a `&mut` argument (item 30)
or a generator holding its arguments (item 31). It does not reject a move out of `self`
in a generic body (item 16), and it cannot tell when a closure escapes (item 19). Drop
glue is built per case, so some owners have none (item 29).

## Target design

The checker becomes an elaborator. Its output is one typed core program, and every later
stage reads only that.

```
AST ──► elaborator (inference, resolution, comptime) ──► typed core
                                                           │
                                 core verifier ◄───────────┤
                                 ownership check ◄─────────┤
                                                           ▼
                                                  HIR lowering (total)
```

### Typed core

The core is a tree in which nothing is implicit.

- Every expression has a settled type. Generic bodies keep their type parameters; an
  instance is the same tree with parameters substituted.
- Every call names its target function or instance and its type arguments.
- Every place is a root with a list of projections (field, dereference, index, variant
  payload), and every use of a place states whether it reads, writes, borrows, borrows
  mutably, copies, or moves.
- Autoref, auto-dereference, literal conversion, operator dispatch, and `for` iteration
  are written out as ordinary calls and borrows.
- A pattern is a test plus a list of bindings, and each binding is a projection of the
  matched place.
- Every node keeps the source span it came from. Generated code keeps the span of the
  quote and the span of the splice that produced it.

Deciding where drops go stays with the ownership check, as it does now.

### Core verifier

The verifier is a small type checker for the core with no inference. It checks that each
call's arguments have the parameter types, each projection is valid for its base type,
each write goes through a writable place, type equality holds including value indices,
and each generic bound is met. It runs in every test build.

This is the soundness mechanism for types. The elaborator may be large and may have bugs.
A bug that produces an ill-typed program is caught by a checker small enough to review in
full. A verifier failure is an internal compiler error, never a user diagnostic.

### Total lowering

A verified core program always lowers. A construct the compiler does not implement yet is
rejected by the elaborator, at the source construct, with a message that says the feature
is not implemented. A refusal after the verifier is an internal error, and each one found
becomes a test. The refusal sites in lowering and the backends become assertions.

### One implementation per construct

- **Calls.** One pipeline: find the callee (bare name, module path, type static, trait
  static, method, UFCS, function value), take its signature, bind explicit type arguments,
  unify the arguments, queue bounds, name the instance. The 17 entry points become callee
  finders that feed this pipeline.
- **Places.** One function turns an expression into a place and reports its mutability.
  Assignment, compound assignment, `&`, `&mut`, method receivers, and pattern subjects all
  use it. Dereference and index go through traits, including a mutable dereference trait.
- **Patterns.** One elaboration to tests and bindings. Or-pattern bindings and bindings
  through `&mut` need no separate code.
- **Type equality and predicates.** One equality over types that compares every value
  index. One "does this type satisfy this" query that answers for traits and concepts.
- **Compile-time values.** One representation for a static value of any type, including
  user sum types, with one rule for reading a part of it and one rule for folding a call
  whose arguments are known.

### Ownership on the core

The ownership check builds its control-flow graph from the core, so it covers every body
the compiler will run: user code, generic bodies, derived and spliced impls, and the
standard library. The rules below are complete for this plan.

- **Places.** Loans and moves are tracked per place with projections, so borrowing
  `p.a` leaves `p.b` usable. An index projection covers all elements of the collection.
- **Function summaries.** Each function gets a summary inferred from its body: which
  parameters its result may borrow from, which borrows it may store into a place reached
  through each `&mut` parameter, and which parameters it moves. Summaries are computed
  bottom-up over the call graph, with a fixed point for recursion, and are written to
  module metadata.
- **Calls without a body.** A call through a trait bound, a function value, or an
  intrinsic uses a summary derived from the signature: any argument that carries a borrow
  may flow to the result and into any `&mut` argument whose type can hold it. A trait
  method's impl must fit the summary its trait signature gives.
- **Stores through parameters (item 30).** Inside a function, a borrow stored into a
  place reached through a parameter must come from another parameter, and the store is
  recorded in the summary. A borrow of a local or of an inner block is rejected there. At
  the call, the root of the `&mut` argument carries each loan the summary says may be
  stored in it.
- **Generators and tasks (item 31).** The value a `generator def` or an async call
  returns carries the borrows of every argument, since its frame holds them.
- **Receivers (item 16).** `self` is a reference. Moving a non-`copy` part out of it is
  rejected in every body. In a generic body a type parameter counts as non-`copy` unless
  a bound says otherwise. The one consuming receiver today, `into_iterator`'s
  `into_iter`, is recorded in the core as a property of that trait method's signature,
  so the ownership check reads it like any other call mode and holds no list of names.
- **Closure escape (item 19).** A closure escapes when the same flow facts show it
  reaching the return value, a store through a parameter or into a longer-lived place, or
  a task spawned outside a `crew`. An escaping closure with no capture list captures by
  move, as chapter 16 says. Any other closure borrows.
- **Task results (item 20).** `get()` returns a borrow of the result the task keeps, and
  `c.errors()` returns borrows of the errors. A result of any type can then be read more
  than once, and each has one owner.
- **Diagnostics (item 34).** Each loan records the expression that created it and each
  value that carries it, so a conflict names the closure and the binding that keeps it
  alive separately.

Drop glue is derived from the core type of each owner by one rule. A closure environment,
a task wrapper, and a coroutine frame each drop what they own, including an environment
that holds no bytes (item 29).

## Phase 3 results

Phase 3 made the typed core the only input of HIR lowering. The old lowerer
(`src/hir/lower.cpp`, about 9,300 lines) and the switch that selected it are deleted.
Run-time and compile-time code are lowered through `src/hir/lower_core*.cpp`, and a whole
program goes through one entry point, `hir::lower_program`, which runs the adapter and then
`lower_core_program`. The driver, the codegen corpus and the test fixtures all use it. The
two corpus tests that compared the lowerers are gone; `codegen_stress_test` covers what
they checked. Implementation chapter 70 describes the result.

Lowering no longer includes `parser/ast.h` or reads an AST node. It uses `origin` and a
function's declaration only as keys into the drop schedule and the ownership facts. The
facts it used to read from the AST are fields of the core that the adapter fills. From
`checked_types` it reads only the type table, `shapes`, `open_shapes`, the drop plans and
the drop schedule. The facts it read from other ownership records moved: whether a call
or a function consumes its receiver is the core's `receiver_mode`, the copies of a generic
lambda are in the drop schedule, and a type's own `drop` is named by its drop plan
(`own_drop_name`), not through the declaration. The reference pass lowering runs on each
function still reads `node_types` and `is_copy`.

Every refusal is classified. A construct the compiler does not build yet is a feature
refusal with a message for the user: 32 sites in the adapter, 10 in core lowering, and 2 in
drop emission. Every other refusal is an internal compiler error that names the item and
the construct: 182 sites in the adapter, 67 in core lowering (one of them covers the
operand checks of 15 intrinsics), and 4 in drop emission. Core lowering no longer aborts
on a malformed tree. Across the test suite and the `known_gaps` programs one internal
error is reached, by a program the checker should reject (item 60).

Items 15 and 36 are closed. `await yield` is the core intrinsic `task_yield`, a
`hir_yield` that waits on nothing, a `reschedule` wait in the storage form and the
runtime's `yield_poll`, which queues the task again; it checks for cancellation when it
resumes. An `on(ctx): body` block is a task (decision 6), so a named one lowers to the
wrapper task `await on(...)` already used. The core path also gained one feature during
the phase: a `pre` on a generator, which the old lowerer built and the adapter had
refused. `storage_codegen_test` is sharded like `check_test` instead of running under a
long timeout.

The verifier runs in every test build. `hir::lower_program` runs it when
`CINDER_CORE_VERIFY` is set, which every test target that compiles programs sets, and a
violation becomes an internal compiler error. Turning it on found three defects. Item 63
is fixed: a `drop` body checked early for compile-time code kept the caller's template as
its own, and lost a `deref` step (rule A2). A write to a nested collection element breaks
rule A4 but runs correctly (item 65). The moves out of `self` of items 16 and 23 break
rule A2; their `known_gaps` programs now record the verifier's message. Rule C8 and the
one cli_test function that writes a nested element are skipped by a list in
`lower_program`; each entry names the item that removes it.

Item 26's message is corrected. A part of a struct-valued `static` that is a struct or a
sum cannot be read at compile time or at run time, and the message now says so. The read
itself is item 26's phase 10 work.

Phase 3 changed the plan in one place. The lowering view stays until phase 12: compile-time
code runs during checking, so the adapter reads the view until the checker emits the core
directly.

## Phase 4 results

Phase 4 so far settled how places are typed and written. Items 12, 21, 33, 37 and 65 are closed, item 38 is closed except for raw pointers, and each closed item has a corpus program checked with `# expect:` (229 to 233). Item 22 closed in phase 3.

- **Element borrows are references.** `cell[T]` and `cell_mut[T]` are removed (decided 2026-11-20). `&v[i]` is a `&T` and `&mut v[i]` a `&mut T`; `index_ref`'s `at_ref` and `index_mut`'s `at_mut` return references, and `list.mutable_cell` became `get_mut`, returning `option[&mut T]`. The checker no longer equates two types, so the adapter's four conversion intrinsics, `hir_cell_set` and the storage form's cell rules are gone. Chapters 14, 15, 42 and 43 changed. One fix came with it: `*m` on a `&mut T` whose `T` was still an integer literal's leaf spent the `int32` default, because `demand_shape` looks through references; a reference's own head is now enough.
- **One place function with an access mode.** The adapter's `place_of` takes a `place_access`. A written or mutably borrowed place (assignment target, `&mut` operand, `&mut` argument, `&mut self` receiver, and every place built under one) is built with `mutate`, which reaches a user collection's element through `*at_mut(&mut v, i)`. The checker records the `at_mut` dispatch beside every read of a user collection. This makes `xs[0][1] = 9` verify (item 65, and the A4 allow-list entry is gone) and `xs[i] += v` compile (item 37).
- **`deref_mut`.** `std.traits.deref_mut` is new, implemented by `mutex_guard` and `write_guard`. A place written through a handle that has it (`*g += 1`, `*g = v`, `g.x = v`, `&mut *g`) records a `deref_mut` step, which lowering and the ownership check use in place of the `deref` step. The guard must be `var`; chapter 30's example changed to say so.
- **Weakening stays at the top.** The checker accepted `&mut T` as `&T` (and `*mut T` as `*T`, and `T` as `&T`) inside a type's arguments, where no single value is there to convert, so `list[&mut int32]` passed as `list[&int32]` reached lowering and stopped with an internal error. Type arguments now compare reference-ness and mutability exactly.
- **Bindings through `&mut`.** A pattern binding reached through a `&mut` subject can be assigned without `mut` (decision 3); one reached through `&` gets an error that says so.

## Risks

- **A fourth representation.** The core sits between the AST and HIR. The cost is offset
  by deleting the side tables, the lowering view, and the ownership check's own AST walk.
  If phase 3 shows the core and HIR are nearly the same tree, they should be merged.
- **Diagnostic regressions.** The checker's messages depend on blame records and AST
  context. The inference diagnostics corpus and the snapshot test must pass unchanged
  through phase 3, and the snapshot is re-based on the core in phase 9.
- **Newly rejected programs.** Checking generated impls and the codegen corpus for
  ownership, and applying summaries, will reject code that compiles today. Phases 1, 7,
  and 8 need time to fix the corpus and the standard library.
- **Summary precision.** A call without a body uses the signature-derived summary, which
  can reject a correct program that passes borrows through a function value or a trait
  method. The diagnostic must say which argument is assumed to be stored and why.
- **Changed semantics.** Automatic move capture for escaping closures and borrowed task
  results change what existing programs mean. Both follow chapters 16 and 28. Owned
  strings change the type of every interpolation, so code that stores or returns a
  formatted `str` must name `string` instead.
- **Compile time.** The verifier adds a pass. It can be limited to test builds if it is
  measurable in normal runs.

## Decisions

These were agreed on 2026-11-15.

1. **The core is a new representation.** HIR stays monomorphic. Ownership diagnostics need
   generic bodies before drops and storage are made explicit.
2. **The plan does not depend on the affine-capability designs.** Every ownership rule it
   needs is stated under "Ownership on the core".
3. **A write through a `&mut` pattern binding needs no `mut` (item 21).** This applies to
   both the method call and the assignment.
4. **Moving out of `self` is rejected in every body (item 16).**
5. **Run-time string bytes are owned by a `string` type (item 24).** `str` borrows from
   it, the way `slice[T]` borrows from `list[T]`. Interpolation, `show`, and the
   `std.string` methods that allocate return `string`, and a `string` lends a `str`
   wherever one is expected. `str` stays `copy`, and the view rules keep the owner alive.
   A string literal stays a `str` of static bytes.
6. **2026-11-17: an `on(ctx): body` block is a task value `task[T, E, C]`; `await on(...)`
   is an ordinary await of it.** It is typed like an `async def` call: `E` is `never`
   unless the body returns `result[T, E]`. `C` is the context the block is written in,
   which is the one that awaits it, not `ctx`: with `C` = `ctx`, the existing context
   check would reject `await on(cpu): ...` in every `async def`. Like any task it starts
   when it is first awaited.
